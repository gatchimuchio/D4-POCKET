## 0. 対象・主語・目的の固定

定義：
- 対象：D4 Pocket＝外部AIが能力を発見・接続・実行・観測・復旧・構成・製品化する汎用ソフトウェア実行基盤。BLUE-TANUKI専用GUI、特定LLM専用フロント、単なるAgent管理画面ではない。
- 主語［目的入力］：製品使用者＝人間のユーザー。達成目的・制約・許容作用・停止意思を指定する。
- 主語［仕事遂行］：AI／LLM／Agent＝目的を解釈し、能力を選択し、必要な実作用を要求し、結果を消費して次作用／完了／停止を決定する実行主体。
- 主語［能力提供］：D4 Pocket＝AIに対する身体・Runtime Operation Shell。実行・監督・接続・構成・観測の製品機構を提供する。AIの判断主体そのものにはならない。
- 主語［認可・監督］：Rust Security Broker＝Authority・Permission・Approval・Credential・Audit・Recoveryと認証IPCの唯一の実行権限境界。AI・Flutter・Adapter・Manifestは権限源にならない。
- 主語［開発］：施工者Codex＝ソース・契約・実行経路を構築する開発担当。製品試験中のCodex CLIは製品側AI Runtimeであり別主体・別権限・別証拠。
- 目的：ユーザーから指示された一般の仕事を、AIがD4経由の実在する複数のソフトウェア能力で遂行し、実結果を次の行為へ反映し、安全な完了または説明可能な停止・復旧に至らせる。構成可能な独立App、Desktop／Mobileの製品品質、既存全能力の継承まで含む。
- 成立連鎖：ユーザー目的／使用権限→AI Task→能力発見・妥当性検査→Broker認可→実Runtime・Tool・Agent・Service作用→実結果・独立照合→AIの結果依存意思決定→次Task／成果物／停止→Audit・Recovery・履歴→再利用／Compose／独立App。
- 失敗条件：ユーザーがGUIでToolを一度起動できただけ／ManifestまたはSchemaが存在するだけ／Mockやfixtureの受渡しだけ／AIの結果を画面だけが受けAIへ戻らない／製品ユーザーの許可を開発者委任で代用／未承認作用を許可とみなす／現候補ではない過去PASSを転記する。

### 0.1 五役の非同一性

| 役割 | 開発・製品における機能 | 権限・責任の帰属 |
|---|---|---|
| 設計者 | 目的→仕様→全系構造→要求の成立条件を定義する | 変更案の論理・責任境界を明示。製品使用許可の発行者ではない |
| 指示者 | 開発目的・施工範囲・制約を指示／製品利用時はAIに目的を指定 | 既に委任した実装・操作の毎回再承認者ではない |
| 施工者 | ソース実装・統合・検証・是正・証拠／Git管理 | Codex等。製品利用者の資格・Broker認可は取得しない |
| 使用者 | 完成製品を利用し、そのAIへ目的・許可条件を与え成果を受け取る | 製品利用操作に固有の許可・取消の意思主体 |
| 責任者 | 設計採否・資産保全・品質判定・署名・配布・出荷を対象別に最終決裁 | 同一人物が兼務しても対象別判断と責任を合算しない |

AIは上記五役へ便宜的に吸収しない。AIの「実仕事の主体」と人間の「製品使用者」は両方成立する。開発施工者のフルアクセスと製品使用者Permissionは相互流用不可。「Owner」は原資料内の歴史的役名／技術識別子としてのみ解釈し、新規規範は上記役割名を使用する。

## 1. 製品の全体系と不変契約

| 層・責任 | 本番producer→consumer | 非許可の越境 |
|---|---|---|
| AI Runtime／Agent | 目的・Task→Capability要求→結果依存の次作用 | 自己Permission、自己Approval、結果・履歴からAuthority生成 |
| Shell Core／契約 | Registry・Runtime／Agent／Session／Task／Workspace／Host／Capabilityの共通意味→Adapter／Broker／利用面 | Flutterの存在を共通実行前提にする、特定AI固有実装をCoreへ固定 |
| Adapter／Provider | Codex CLI・異種Runtime・MINIDORA・BLUE-TANUKI等の実在端点→共通要求・応答 | 外部metadataを信頼・権限へ昇格、秘密を直接公開、無監督fallback |
| MCP／A2A／Host／Tool | Catalog／Card／Message／Task／Artifact→正規化・現在条件検査→実作用 | 宣言情報だけでTool実行、Host／Task／Runtime間の権限横流し |
| Rust Security Broker | 認証IPC→Capability→Permission→Approval→実作用→AuditEvent→RecoveryAction | 未認可実行、Audit不能時の成功発行、秘密表示、replay／非冪等再送 |
| ソフトウェア緩衝基盤 | 差異観測→意味保持調停→許可済み原操作→実結果／副作用照合 | 別のpermission engine、検査緩和、単純retry成功の根因解消扱い |
| Flutter Desktop／Mobile | 使用者への目的入力・許可・状態・停止・検査・復旧の表現 | UIをAIの内部連続実行Controller／権限源にする、秘密実値を保持する |
| Compose／Export／Installer | 実能力の依存・選択・合成→独立実行物→導入・更新・復旧 | Manifestだけで能力成立、署名・独立identityを偽装 |
| Evidence／Release | Source・Contract・Runtime・artifact・OS・試験・Audit→対象別QC／QA→出荷判断 | 開発PASSから製品保証、旧CLOSEDから新候補保証、責任者GOの自動生成 |

不変集合：
1. Authority／Permission／Approval／Audit／Recovery／Credential／Content Exposure（none・hash_only・summary・redacted・full）／Workspace・Host・Session・Task実体束縛／秘密／署名／replay／TOCTOU／hardlink・symlink／process tree cleanup／fail-closed／可逆性。
2. ユーザーの既存有効許可の範囲内ではAI内部手順ごとに手動確認を強制しない。新規scope・失効・不可逆操作・本人固有意思が要求された対象作用のみ製品の正規確認経路へ進む。拒否された作用は別経路で迂回しない。
3. AIが外部Tool結果を「資料」として消費することと、Tool結果が「権限を作る」ことを混同しない。後続Taskは現在の条件で再認可・新しい識別子を使用。無限自動連鎖・非冪等無条件再実行を禁止。
4. 過去実行の再実行／分岐は新Session・新要求・新Audit。既存Auditを改竄せず、旧ApprovalやPermissionを自動継承しない。
5. 日本語意味正本を保持。通信規格・ABI・製品固有token・外部APIの原形は局所例外。HDS／MINIDORA／BLUE-TANUKI固有の非公開実装、内部脳、独立のRAG／知識基盤／Web検索／Code Interpreter／LLM MemoryをD4 Coreへ移植しない。

## 7. QE・受入・製品完成

- 工程原則＝QE_DESIGN→QE_BUILD［N01〜N11／P／BUF／全OSを同一設計から一括施工］→SYSTEM_SHAPED→BUILD_COVERED→QE_QC→QE_QA→QE_RELEASE_REVIEW。
- 「一括施工」＝完成製品全体のproducer／consumerを最初の実装対象集合として固定し、全能力群を跨いだ接続を連続構築すること。単一巨大commit・無検査一発生成・安全ゲート後回し・各OS実機の同時入手を要求する意味ではない。W／B／P番号のCLOSEDを次の機能実装開始の前提としない。
- BUILDの実装中も権限・秘密・作用の即時負例を保持。全体機能の実配線完成をBUILD_COVEREDに要求。意味あるBUILD_BATCHごとの限定compile／安全検査とGit閉包は残す。全suite／正式QA／Q0凍結は小単位ごとに繰り返さない。
- 最終Q0〜Q7は既存の正式試験識別子。Q0候補凍結→Q1横断→Q2故障・回復→Q3権限・秘密→Q4長時間・資源・性能→Q5installed・導入・更新→Q6証拠→Q7責任者最終決裁。旧候補Q0/Q1の履歴は現候補へ流用しない。正式開始時にDEFERRED解除条件を独立に確認する。
- 全製品完了＝全N／旧必須P・C・BUF／OS別実consumerの構造完成＋同一候補の全体QC＋対象別QA＋Strict Release Gateの必須条件＋責任者の正式配布判断。Windows限定技術完成と五OS全製品完成を同一状態にしない。Release承認前のrelease_readyはfalse。
