## 1. 最上位思想：QEとQC・QAの作用分担

本案件における品質の意味は、観測可能な実体について、現在の根拠・整合・因果・現実適合を基に妥当性を判定し、新たな反例があれば対象・前提・設計・実装・検査まで必要箇所を更新すること。最上位の方法論はQEであり、その内部にBUILD、実物QC、対象別QAを持つ。これは本プロジェクトの運用定義であり、一般規格の普遍的な階層と主張しない。

```text
QE_DESIGN（目的・要求母集団・因果・設計・責任境界）
     ↓
QE_BUILD（実装し、実consumerを接続。小単位は意図的再同期）
     ↓
SYSTEM_SHAPED（限定した実作業が入口から結果まで縦断）
     ↓
BUILD_COVERED（必要な機能群とconsumerの結合形状を全件照合）
     ↓
QE_QC（完成した結合実物の観測・全体検査・根因是正・同条件再測定）
     ↓
QE_QA（QC証拠に基づき対象・版・OS・条件別の保証可否を判定）
     ↓
QE_RELEASE_REVIEW（Owner本人の独立した署名・公開・不可逆判断）
```

| ステージ | その時点で成立させること | 成立しないこと |
|---|---|---|
| `QE_DESIGN` | 上流目的と実装可能な関係・意味・反例を固定 | 仕様書だけで実動作完成を宣言しない |
| `QE_BUILD` | producer→consumerの実接続。安全重要箇所は即時に拒否・停止確認 | 個々の小単位に全suite・全数QC・QA票を要求しない |
| `SYSTEM_SHAPED` | 安全な限定条件で一つの仕事が実際に縦断 | fixtureや部分的経路をinstalled製品へ昇格しない |
| `BUILD_COVERED` | 全要求の結合先・残差・禁止境界を照合 | 仕様面の一覧だけで成立、未接続を黙って除外しない |
| `QE_QC` | 実物を包括的に検査・是正・同条件再試験 | 旧候補のPASSで新候補を保証しない |
| `QE_QA` | 適合が成立する対象と条件だけ保証可能と判定 | 全OS、全利用者、将来までの保証を作らない |
| `QE_RELEASE_REVIEW` | Ownerが出荷・署名・公的主張の採否を決定 | Codexが自分でOwner GOしない |

要求・設計・BUILDのすべてに品質責任・根拠照合・再設計は残す。しかし `QE_BUILD` の構文・型・限定疎通を `QE_QC` と同じ完了判定にしない。元 `BUF-R08` の「全開発で品質成立を扱う」という内容は、QEの全期間規律として保持する。**QCを放棄するのではなく、対象となる実物が揃ってから集中的に実施できるよう配置する**。

### 1.1 タスク分割とBUILD_BATCH

小単位を分割する主目的は目的ドリフトの抑止と作業対象への再同期である。開始・中断再開・担当交代のたび `AGENTS.md`、現在の指示書、対象の目的、HEAD/dirty state、producer／consumerを読み直す。小単位の途中状態は `CODE_PRESENT`／`WIRED`／`BUILD_GAP`／`BLOCKED_AUTHORITY` とする。モデル内部記憶の消去を保証する意味ではない。

`BUILD_BATCH` は複数小単位を束ね、一つの実際の仕事・consumerを前進させた成果の施工・技術確認・Git保全単位とする。各小単位で全Rust suite、全Flutter suite、全数Conformance、長時間試験、QA判定、バックアップ回転、commit/pushを行わない。小単位の単なる分割数を品質指標にしない。ただし、安全に必要な拒否検査と既存の正式release検査は適用時点で必須。

## 2. D4Pocket製品の目的と不変の責任境界

D4PocketはAI Runtime、Agent、Tool、Local Serviceを操作する**汎用のDesktop-first Runtime Operation Shell**であり、BLUE-TANUKI専用GUIではない。BLUE-TANUKIはAdapter境界後方の参照Runtimeである。C/J/M、HDS-BRAINの非公開判断機構をD4の汎用Shell Coreへ埋め込まない。D4側の権限・実行・記録・公開判断は現行D4の所有者と契約に従う。

製品の保持対象を構成する主要能力・責任面は、Runtime/Agent/Session/Task、Provider/Model、Compare、Handoff、Workspace/History/Evaluation、Credential/MCP、A2A/Host/Adapter、Compose、Export/Module Pruning、Installer/Update/Rollback、**Windows・macOS・LinuxのDesktop、およびAndroid・iOSのMobile**の既存契約である。**本書はこれらのrev5機能要求本文を省略・代替しない。** 過去にCLOSEDのAcceptanceは履歴として保存し、再現性ある回帰で破損したときだけ範囲限定で再開する。

**実行責任の固定：**

| 所有面 | 許される責任 | 禁止する越境 |
|---|---|---|
| 操作者（`Owner`） | 明示する目的、承認、公開・署名・不可逆判断、最終GO | 言語模型／ログからOwner同意を推定しない |
| 権限を持つBrokerと基盤（`Rust Security Broker`／`Shell Core`） | 現在のAuthority、Permission、Approval、Audit、Recovery、Owner control、実行前照合 | metadata／Agent提案を権限として採用しない |
| Agent実行系と接続層（`Agent Runtime`／`Adapter`） | 与えられた契約で作用を提案・実行し、型付き観測を返す | 自己Permission昇格、Host/Workspace越境、結果の権威化 |
| 緩衝基盤 | 許可済みの変換・隔離・環境固定・状態調停を行い、元Toolの動作を成立させる | 独自Authority、OS保護解除、意味変更、失敗を報告だけで消す |
| UI層（Flutter／Desktop／Mobile） | 許可済みの公開状態・要求・結果を表示 | 任意Owner Approval生成、監査のfinality決定、raw secret表示 |
| 初期診断・問題一覧（`Setup Doctor`／`Problems`） | 読取り診断、問題や回復経路の案内 | これだけを緩衝基盤の実作用と呼ばない |
| Schema/Conformance/Fixture | 入出力形式、拒否条件、局所の適合性を検査 | 本番consumer成立／配布可能性を自己証明しない |

保持する禁止：権限昇格、資格情報の露出、Owner UI自動承認の偽装、Approval再利用、secret/hardlink/alias/TOCTOU越境、Workspace間・Host間のAuthority共用、監査不能時の成功投影、未監督process、fail-open、誤ったrelease claim。Permission／Approval／Audit／Recovery／Content Exposureなどの既存安全境界を緩和しない。

### 2.1 D4Pocket固有の開発環境・保全

- 開発の検証正本はローカル／実機。自動CI、push/PR必須チェックを新設しない。D4で明示許可された `workflow_dispatch` 手動Actions補助、一時検証ブランチと成功commitのみmainへ取り込む条件を維持する。BLUEの手動Actions不許可を輸入しない。
- 基本はdirect-main、単一writer。他者のdirty差分をreset/clean/revert/overwriteで消さない。
- D4の2世代復旧refは **`refs/tags/codex/backup-main` と `refs/tags/codex/backup-main-prev`**。BLUEの同名`refs/heads`方式へ無断変換しない。ref種別を省略しない。実編集前の保全、バッチ後のremote HEAD・復旧点照合を維持する。
- D4固有のRust、Flutter、**Windows／macOS／Linux／Android／iOS**、OSごとのsandboxとコード生成、契約・言語基底、Release Gateの実装条件は現行の適用契約から引き継ぐ。Windows-firstは開発・検証の優先順位であり、Linuxを対象母集団から除外する意味ではない。通常Releaseの `task_execution=unsupported`、`release_ready=false` を変更する権限を方法論から作らない。

### 2.2 Linuxを独立した製品対象OSとして扱う（今回追加）

**Linuxは「非Windows」や「Ubuntu/WSLでビルドできた」の一語に埋め込まない。** D4Pocketの汎用Desktop製品と緩衝基盤を構成する対象OSとして、Windows・macOS・**Linux**を個別に識別し、MobileのAndroid・iOSとも区別する。Linuxの対応契約は、既存Broker／Shell Coreの権限を再利用し、Linux固有の実行条件を検査して成立させる。Linux未実装部分は要求母集団から除外せず`BUILD_GAP`として管理する。

| 区分 | 何を確認するか | 証明しないこと |
|---|---|---|
| `LINUX_NATIVE` | Linuxを直接起動した対象マシン／VM上で、Linux用Desktop GUI・Broker・Adapter・Agent Task・IPC・OS境界・保存と停止／復旧・配布物を対象契約で確認 | WindowsやmacOSの同等動作、他Linux環境での動作、未試験機能の完成 |
| `LINUX_WSL_DEV` | WSL内Ubuntu等におけるRust/Flutter/Toolchainの開発用compile・局所試験・CLI操作、Linux filesystem上の動作 | ネイティブDesktop製品、一般Linux利用者のインストール・GUI・Owner認可・安全の成立 |
| `LINUX_WSLG_X11` | WSLg上のX11画面可視性、局所的なFlutter表示・UI試験 | LinuxネイティブX11/Waylandの双方、GPU性能、導入済み製品・一般配布 |
| `LINUX_HEADLESS` | GUIを使わないLinux Broker／Toolchain／CLI経路の限定動作 | Desktop利用者の画面、Linux用installer、native Owner確認 |

現行資料には開発用WSL/WSLgと別に、**2026-10-22 GitHub手動Action #107でLinux installed MCPの合成X11（Xvfb）限定検査PASS**が記録された。READMEの従来記述はこの差分を同期する必要があるが、**Linuxネイティブでの全製品機能・一般の導入済み製品・通常Releaseが受入済みだとは主張しない。** Linux対応を進める際は、対象ディストリビューション／版、kernel・アーキテクチャ・libc、GUI backend（X11／Wayland）、filesystem、sandbox・資格保管、起動・終了責任、成果物種別を先に宣言する。特定distribution・display server・installer形式のサポートを未決定のまま「全Linux対応」と呼ばない。

既存のLinux開発用検証は継承するが、Linux製品の入口（Desktop UI／native Owner認可／Broker IPC／Runtime・Adapter／実Agent Task／Audit・Recovery）について**同一プロセス系列の実作用**を確認する。新しい権限源・Linux特別許可・無監督process・secret露出・失敗時fallbackは導入しない。Linux側のOwner操作・native bridgeなどに実装不足があれば契約を推測で埋めず未接続として記録する。OS別の「ビルド可」「実経路可」「installed可」「配布可」「保証可」を別状態にする。

## 4. 緩衝基盤の対象・目的・原理

### 4.1 全数母集団を出発点とする

D4Pocket開発で発生したボトルネックは、開発環境、依存とABI、UI/OS automation、ネットワーク、Workspace/Secret、Runtime、設計誤認、検査器の失敗、証拠取得不能、工程管理まで**全件を調査対象**とする。吸収しやすい例だけ選んで設計しない。各事象を `元証拠→目的→干渉境界→根因の確度→既存対処→介入候補→安全境界→必要実験→残余` と結ぶ。

2026-10-11時点の履歴記録ではB0は356 Actions run中203 failureを一意化し、取得できないjob log75、原因不明run19、legacy job級の原因証拠不足17が残る。B3は全153の**原因対応行の分類**をCLOSEDにした。これらは**全エラーの根因特定・全ボトルネック自動吸収・品質完成ではない**。記録に存在しない事象や未取得ログはUNKNOWN／取得不能を維持する。最新母集団は施工時に再取得し、古い件数で現在値を上書きしない。

### 4.2 実行緩衝の操作定義

**緩衝とは、別々のソフトウェア境界が要求する前提の衝突に対し、現在の実行権限の内側で、元要求の意味を変えない変換・隔離・環境固定・状態調停・既存Tool機能再利用を実際に作用させ、上位Agentに反復調整を戻さずに元の操作を成立させること**である。検知・エラー整理・画面表示は必要なら補助であり、主体機能ではない。

```text
Agentの元目的／元要求（非権限）
      ↓
既存Broker：Runtime/Task/Host/Workspace/Permission/Approvalを現在照合
      ↓
非権限調停：干渉と条件の型付き観測 → 候補 → 現在条件の検証
      ↓（許可済みの可逆・限定作用だけ）
実作用：変換／環境・一時領域固定／隔離／状態調停／既存Tool機能利用
      ↓
元Toolchain・OS／Runtime（元の操作を実行）
      ↓
結果・意味・安全・cleanup・副作用・介入前後の独立検証
      ↓
Broker Audit/History → bounded投影 → Agentが元目的を継続
```

変換がlossy、互換性が不明、OS保護による正当な拒否、Owner未承認、secret露出、元要求と別の成功条件へ書換える行為は適用不能。未知を勝手に `吸収不能を実証` と呼ばず `未観測`／`未成立`／`BLOCKED_AUTHORITY` として残す。

### 4.3 本体の作用群（採否は個別証拠による）

| 作用族 | 具体的に吸収する境界 | 不変条件と反例 |
|---|---|---|
| 互換変換 | API/Schema/文字コード/改行/パス表現／可逆Protocol変換 | round tripと元の意味が一致しなければ無作用 |
| 依存隔離 | toolchain/SDK/ABI/Version/lock graphの実行条件衝突 | 無断依存更新、未承認OS設定変更、別source成功で偽装しない |
| 一時環境固定 | Host/Agent/TaskのTEMP/TMP、artifact staging、cache | 別Task/別Host/Workspace汚染とsecret露出を防ぐ |
| 状態調停 | process/port/listener、stale state、partial artifact、復旧 | 状態を偽装せず、復旧不能ならfail-closed |
| 既存Tool機能 | tool自身の固定オプション・sandbox・atomicな操作 | 正式契約の意味を変えるwrapperへ逃げない |
| 非介入 | OS防護、Approval欠落、意味非互換、UNKNOWN | 安全な不成立を保持。勝手な再試行・迂回はしない |

### 4.4 元Taskの成立条件と緩衝試験を分離

`BUF-T09`等は**緩衝機構の品質試験ID**であり、Agent Taskの元目的・成功条件ではない。元要求の識別・入力hash・元目的の成立判定と、緩衝の成功条件／証拠は別フィールド・別責任で保つ。現行Brokerが `元要求.成功条件ID=BUF-T09` を固定する設計は、元Taskの目的判定と混同する危険がある。将来の接続設計では両者を区別すること。ただし、既存v2 Schemaや過去B4-L2を本書の提案だけで変更しない。

`specs/buffer_intervention_record.schema.json` v2は非Git Workspaceのsource commitを未取得として記録できる一方、**未取得時に `吸収成立` を禁止**する。汎用基盤の達成には、非Gitでも入力・toolchain・workspace・実行条件の同一性を検証できる別の証拠契約が必要となる可能性がある。採用する場合は、Gitの場合と同等の安全性を正常・否定・差替え試験で実証し、他の証拠欠落をごまかす用途にしない。現在のv2の判定を勝手に緩めない。

## 7. 証拠と成功判定

証拠は `CONFIG`／`INTERNAL_STATE`／`FIXTURE`／`LIVE_RUNTIME`／`EXTERNAL_EVIDENCE` を区別する。実機試験でも「試験Broker＋合成Owner」「本物のCodex CLI」「installed UI」はそれぞれ別の証拠階層であり、相互に昇格させない。実行した正確な版、Host、Workspace、source、Toolchain、command、exit、結果hash、差異、未実施理由を記録する。raw本文・秘密・実資格・非公開HDS原典は公開証拠へ混入しない。

緩衝の`吸収成立`は、同一条件下で **(A)元失敗の観測、(B)許可済み介入の作用、(C)元Toolと元目的の成果、(D)意味同等性、(E)介入なしとの比較、(F)副作用と問題移転なし、(G)必要なcleanup/Recovery、(H)独立した検証根拠** を満たした対象・版・環境の範囲でだけ主張する。分類票、単体再試行PASS、エラー書換え、fixture合格、別Hostの成功は代用不可。

主要評価値：反復調整回数、Agentへ差し戻した処理数、同一原因再発数、介入前後の完了率、経過時間、CPU/メモリ/disk/handle/process負荷、既存正常経路への回帰、誤吸収・権限迂回の有無。閾値はベースライン取得後に設定し、後出しでPASSする閾値へ調整しない。十分な母数がない場合は効果`未検証`。

## 9. BUILD_COVERED・QC・QAの受入条件
