## 0. 結論・本書の射程

D4 Pocketは、**AI／LLM／エージェントが必要な能力を発見・選択・接続・実行・再利用するための汎用的な「四次元ポケット」**である。単なるGUI、単一Agentの管理画面、特定LLMの外付けツール、BLUE-TANUKI専用フロントエンドではない。

- **能力を使う主体**：AI／LLM／Agent。人間も操作可能だが、AIの実務consumerを第一級として扱う。
- **権限・責任の主体**：人間のOwner。Agent、Tool結果、Adapter、UI、Manifestは権限源ではない。
- **D4の目的**：異なるRuntime・Agent・Tool・Serviceを、共通契約・Owner認可・監査・復旧のもとで実際の仕事へ利用可能にする。
- **成果状態**：一般利用者がインストールした製品で、AIが許可された仕事を完結し、結果・根拠・失敗・復旧状態を人間と次のAgentへ引き継げる。能力の追加・組合せも同じ責任境界で扱える。

本書は「今回何を追加するか」の技術要求を整理するものであり、既存rev5の採用機能・Acceptance、`BUF-R01〜R09`、`BUF-T01〜T24`、P0〜P13、Q0〜Q7、2026-10-22 QE正本3点の要求母集団を置換・削減しない。従来の局所CLOSEDは保持し、未実証を完成扱いしない。新しい要求IDは**導入対象を追跡する補助ID**であり、過去のIDを改名しない。

## 2. 不変のアーキテクチャと責任境界

| 層 | 主責任 | 禁止事項 |
|---|---|---|
| AI／Agent／外部Runtime | 依頼解釈、能力選択・利用要求、結果の継続利用 | Permission発行・自己承認・外部結果の信頼昇格 |
| Adapter／Provider／A2A／MCP | 異種プロトコルの正規化、明示Capabilities・制約の提示、実作用の橋渡し | Adapter metadataをAuthorityとみなすこと |
| Shell Core／Contract | Runtime・Session・Task・Workspace・Capability・状態遷移の共通表現 | 特定Runtimeの判断・BLUE-TANUKI HDS-BRAINを埋込むこと |
| Rust Security Broker | 認証IPC、Permission、Approval、Credential、実行制御、Audit、Recovery | GUI・Python参照実装・Agentへ権限判定を委譲すること |
| Flutter Desktop／Mobile | 人間可読な操作・承認・状態・問題・証拠・復旧UI | 機密値・Owner資格の保持、権限解釈・実行側の迂回 |
| 配布／独立App | source・artifact・identity・導入状態の真正な対応 | Manifest存在だけで完成App・署名・配布を主張すること |

各機微作用は`Capability → Permission → Approval → AuditEvent → RecoveryAction`の対応と、`none / hash_only / summary / redacted / full`の内容露出規則を維持する。秘密の境界、再実行禁止、nonce/replay、失効、Workspace／Host隔離、process tree cleanup、external Audit anchorは既存契約を継承する。非公開HDS原理や別リポジトリの実装をD4に移植しない。

## 3. 実装要求（既存継承＋未接続consumerの閉包）

### D4-N01：実仕事の一貫したTask経路

**入力**：Ownerの仕事要求、明示されたAgent/Runtime、Workspace、対象Host、Capability、実行制約、期待成果。  
**作用**：Agent起動・Task受理、Brokerによる資格・権限照合、元Tool作用、結果受領、継続／完了／中断。  
**出力**：成果物と帰属、状態遷移、Task/Tool/Audit相関ID、再生可能な検証証拠、失敗時Recovery。  
**保持**：通常Releaseでサポート未宣言の間は実Taskを拒否。単にmetadataの`unsupported`を書き換えない。成功・拒否・cancel・deadline・再起動時のprocess/credential cleanupを同一境界で観測する。

### D4-N02：AI Taskから実Toolへ往復する能力経路

既存MCP stdio／Tool Centerを再利用し、Agent Taskの機能要求→実接続Toolの発見→限定選択→必要なOwner認可→実Tool呼出し→結果の正規化・露出制御→Agentへの結果帰還→後続Taskを閉じる。現状の人間操作による一回Tool実行と分離する。未発見Tool・資格不足・不正結果・接続喪失・非冪等作用はfail-closedとし、PermissionをTool結果から作らない。

### D4-N03：Runtime／Provider／Agentの汎用接続

現行`codex-cli`中心の稼働Adapterを参照witnessとして保持し、現行Contractで表現可能な独立実装を増やす。MINIDORA等はAdapter接続候補でありCoreへ内蔵しない。登録→能力検査→実用可能性表示→限定Task実行→結果返却までを各Runtimeで試験する。未接続IDや`unsupported`能力を実行可能に表示しない。Provider認証・CredentialはBrokerの管理境界を守り、暗黙fallbackを行わない。

### D4-N04：Agent間の実仕事引継ぎ

既存P2 Compare／P3 HandoffのCLOSED範囲を再実装せず、外部A2Aに対するAgent Card metadata、Task、Message、Artifact、Stream／停止の実対応を切り分ける。Handoffではcontext・成果・diff・検査・失敗をconsumerが再利用できるようにし、旧AgentのPermission／Approval／Credentialを継承しない。汎用外部相互運用は明示した対象Provider・版・作用のみ受入れる。

### D4-N05：能力発見とCompose

現行Composeの参照ID入力／`manifest_only`を保持しつつ、実Runtime・Tool・Agent・Capability登録簿との実在照合、互換性・依存・不足の提示、承認される構成への接続を成立させる。ManifestをAuthorityや実行保証にしない。正確な出力状態は`manifest_only`、`wired`、`build_verified`、`installed_verified`を別フィールド・証拠で表す。実装可能な既存契約を先に再利用する。

### D4-N06：独立App ExportとModule選択の実化

選択された構成と新規App／Audit identityを、独立した実装物・Runtime consumer・Installerへ渡す。Developer-only Windows bundle buildの存在を製品UI経路の完成と混同しない。生成Manifestがbundle runtimeに消費され、選択した機能が実行可能、必要な安全Coreが保持、外した機能が機能上除外されることを確かめる。binary pruning・容量・性能を主張する場合は実測したartifactを固定する。署名・配布・Owner確認は独立Gateとする。

### D4-N07：AIによる拡張提案から検証済み導入まで

既存AI Edit `proposal_only / review_required / files_written=false`は安全な現在状態として維持する。新しい拡張が必要な場合は、AgentがContract・Schema・test・実装候補を提案し、Developer/Ownerが独立に差分を審査・検証・導入する開発経路を設ける。**製品Runtimeの自己改変・自己承認を認めない**。能力発見・登録・再利用の製品面と、リポジトリを編集する開発面を混同しない。

### D4-N08：B5自己適用・緩衝の作用検証

既存`BUF-R01〜R09`／`BUF-T01〜T24`の全数母集団とB0〜B4の成立範囲を維持する。B5のOneDrive因果、loopback/TLS failure、SAC、process cleanup、自己適用、長期・資源影響を介入前後・同条件で測定し、根因未観測を推測で埋めない。B6では全既存consumerへの回帰を統合QCとして確認。新たな安全重大欠陥がなければ、B5の未解決項目すべてをProduct Buildの一律停止条件にしない。

### D4-N09：Ownerが扱える製品操作と復旧

Agent Center、Problems、Evidence、Recovery、Runtime、Authority、Credential、Setup Doctor等の既存画面を壊さず、AIが実行中のTask、使用能力、許可待ち、実結果、失敗原因、回復選択を人間が理解・操作できるようにする。操作性は利用目的と実作業から評価し、形式的項目数だけで完成としない。対象画面・表示密度・アクセシビリティは実機で確認する。

### D4-N10：OS・インストール・更新・配布

Desktopは**Windowsを最初の製品化優先対象**、macOS・Linuxは独立した必須対象。Android・iOSのMobile Device Link、資格保護、配布も既存要求から削除しない。LinuxのXvfb/X11・headless Wayland・WSL／WSLg／hosted証拠を一般Desktopの実機証拠へ拡張しない。Windowsのinstaller／first-run／Broker installed／Setup Doctor／Distribution identity、Linux同一source update・rollback・uninstall・署名、macOS配布、Mobile物理端末とNative Linkを各consumerごとに確認する。更新・復旧では利用者データとAudit履歴を保持する。

### D4-N11：全要求の追跡と証拠の健全性

既存rev5、P/B/Q、Release Blocker、今回N01〜N10を**要件→producer→consumer→OS→実装path→試験→証拠source SHA→状態**で追跡する。`CODE_PRESENT / WIRED / BUILD_GAP / BLOCKED_AUTHORITY`を区別。実機で確認していない事実を`LIVE_RUNTIME`や正式QAに昇格せず、既存のFAILと新しいPASSを別の版・条件として保持する。strict日本語監査の残差は意味不整合と既存token検出に分類し、無差別置換で消さない。

## 4. 統合受入れシナリオ

1. **Task**：非Mockの通常製品で1つの依頼をAgentが受け、Owner許可の範囲で実作用し、成果・Audit・復旧状態まで同一相関IDで確認できる。
2. **Tool**：Agentが実MCP Toolを使い、Tool結果を入力として後続行動を変える。秘密値・Permission継承はない。拒否・中断も成立する。
3. **異種Runtime**：少なくとも2種類のRuntime／Agentで同じ契約を消費し、能力差・拒否・結果を正しく表示。受入れ対象と非対象を明記する。
4. **引継ぎ**：独立Agent間で成果・context・diff・testを受け渡すが、権限の自動移譲なし。外部A2A対応は別に実証する。
5. **Compose／Export**：構成選択から独立artifactの実消費とinstalled動作まで同一identity・hashで追跡。未実装のOSには完成を主張しない。
6. **障害・復旧**：cancel／deadline／kill／replay／ネットワーク不通／credential失効でfail-closed、process・temporary stateを残さず、監査を失わない。
7. **製品UX**：Ownerが通常インストール済みUIから必要操作と復旧を完了し、画面だけで実行不可・許可不足・失敗を識別できる。

各シナリオは機能正例だけでなく安全負例、実際のsource/consumer、OS、版、使用したfixture、未観測範囲を含む。既に同条件で受入れ済みの部分を再試験だけのために繰り返さない。

## 5. 品質・完成の判定

- **QE_DESIGN**：対象・目的・要求母集団・接続先・安全境界と反例を固定。
- **QE_BUILD**：既存能力を継承し、本番のproducer→consumerを追加接続。
- **SYSTEM_SHAPED**：1件の実仕事が通常入口から結果／Auditまで通る。fixtureだけでは不可。
- **BUILD_COVERED**：必要consumerをOS別全数照合。未接続を隠さない。品質合格ではない。
- **QE_QC**：同一候補の実物で結合・安全・長期・性能・復旧・相互干渉を試験し、是正・再試験。
- **QE_QA**：結果の射程を`QA_SCOPED / QA_NOT_ESTABLISHED / OUT_OF_SCOPE`に分類。
- **QE_RELEASE_REVIEW**：正式Q0〜Q7、署名・配布identity・鍵・外部tamper証拠を踏まえてOwnerが最終判断。

`release_ready`や`task_execution`を達成宣言のために編集しない。技術証拠がそろった後、既存Release Gateが許す状態遷移と独立Owner判断だけで変更する。性能・資源効率は比較環境と測定条件を固定し、既存製品より悪化しないことを確認する。完成を小さなMVPへ再定義せず、機能開発・実物QC・対象別QAを有限の工程で完結させる。
