## 0. 到達目標と施工順序

最終成果は、AI／LLM／AgentがD4 Pocketから必要な能力を発見・選択・組合せて**実際の仕事を遂行**し、人間のOwnerが権限・監査・障害復旧・更新・配布を制御できる、一般利用者向けの独立製品である。Windows優先、Linux・macOS・Android・iOSの既存要求を残す。特定Agent、単一Runtime、GUIの存在、テスト通過のいずれかに製品完成をすり替えない。

重要な順序は以下とする。

1. **W00 現物固定**：既存rev5要求とH01〜H07健全化後のコード・証拠を突き合わせる。
2. **W01〜W03 実仕事の閉包**：通常ReleaseのAgent Taskを実動させ、Toolへの往復と異種Runtime／Agentの接続を成立させる。
3. **W04〜W05 能力の組合せ・独立配布**：Compose、AI Edit提案経路、Export、Module選択を実consumerまで閉じる。
4. **W06〜W07 OS別製品化**：一般利用者の通常インストール済み環境でUI・Broker・配布・復旧を証明する。
5. **W08 実物の品質決裁**：B5／B6の残件、結合QC、正式Q0〜Q7、独立Owner判断を終える。

これは依存順であり、単なるファイル編集順ではない。独立課題は並行してよいが、後段の合否を前段の代用品にしない。工程の中間出口をMVPや正式Releaseと呼ばない。

## 3. 各Gateの成立条件と停止規則

### G0：設計と現物の一致

- 各要求に一意のOwner/Agent主体、操作対象、入力、出力、Authority境界、producer、consumer、OS適用範囲が存在する。
- 既存P／B／QのCLOSED・OPEN・DEFERREDを当時の条件付きで写し、名前だけの「全面未完了」「全面完了」を作らない。
- 未実装と未観測を分離する。外部接続先・資格・物理環境が不足する場合は`BLOCKED_AUTHORITY`または`EVIDENCE_MISSING`として保持。
- 事実を覆す新証拠が得られた要求のみ、出自と理由を付けて状態更新。

### G1〜G3：通常Agent Taskの作用閉包

- `task_execution=unsupported`のままならG1は未成立。メタデータだけの書換えは禁止。
- 正常例は本番機能を持つ実AgentがTaskを消費し、結果がTask／Session／Workspace／Auditへ返ること。
- 異常例は無許可Tool要求、期限切れ・失効資格、異常Agent出力、競合、ネットワーク断、終了・再起動で安全状態へ移ること。
- Tool結果から権限を発行しない。次AgentへHandoffしても前Agentの許可が複製されない。
- 証拠はtest-only `r2-e2e`／fixture／normal Releaseの別を明記する。

### G4〜G5：生成物と実行物の接続

- Composeは存在する能力と権限範囲を検査し、構成が使える条件を通知する。
- AI Editは提案と検証済み導入を分離し、製品Runtime自身のソース書換え・独断採用を認めない。
- Exportの独立Manifestが実Bundle／Runtime側で消費される。選択された機能が使え、非選択機能が除外され、安全Kernelが残る。
- Artifact・App identity・配布署名／検証・更新可能性を一意に追跡し、Owner承認待ち事項を通過扱いにしない。

### G6-WIN／G6-OS：製品としての実機条件

- 操作可能なUI、Broker、Agent／Tool、権限、Audit、復旧を同一のインストール済みartifactで試験する。
- Windowsは優先して閉じるが、Linux・macOS・Mobileの既存要件を削除しない。OSがない場合は最終QAで範囲未達と判定する。
- Linuxは通常のGUI Sessionで検証し、Xvfb・X11のみ、WSL、headless Wayland、fixture経由の成功をそのままnative Desktopの正式証拠に転用しない。
- 更新失敗後に元状態と利用者データ、Audit履歴へ帰還でき、再試行時に権限や秘密が逸脱しない。
- 実機計測とソースの出自・Build／Release identityが一致する。

### G7：QC／QA／Release Review

- `QE_DESIGN → QE_BUILD → SYSTEM_SHAPED → BUILD_COVERED → QE_QC → QE_QA → QE_RELEASE_REVIEW`の順序を守る。
- B5の残件は影響度に応じて実測・是正し、B6で全対象consumerの回帰・相互干渉を統合検査する。
- Q0〜Q7は**凍結した同一製品候補**で要求に応じ実施する。2026-10-07旧版の限定Q0/Q1結果を現候補の正式QAへ自動転用しない。
- QAは`QA_SCOPED / QA_NOT_ESTABLISHED / OUT_OF_SCOPE`の射程付き判定。未実施をPASSとしない。
- `release_ready=false`・未解決Blockerは、正当なGateと独立Owner判断を経るまで保持する。

## 5. 有限作業単位の運用

各`BUILD_BATCH`は「一つの必要consumerが実際に何を消費できるようになったか」を中心に組む。

1. **Before**：対象要求ID、既存受入れと新規差分、現在HEAD、入力・出力・Authority・実producer→consumerを確定する。
2. **Build**：最も小さい**意味的に完結する**縦断差分で実接続を作る。複数言語・層を跨ぐ必要があれば同一Batchに含める。
3. **Local verification**：対象の正例・負例・Schema・契約・実動経路を最低限試験する。Mockやfixtureの場合は表明範囲を限定する。
4. **Integrated verification**：節目ごとにConformance、Rust、Flutter、OS別動作を要求に従い実行する。編集1件ごとのフルテスト・commit・pushは行わない。
5. **Evidence & report**：成果、現在の状態、証拠SHA／OS／手段／結果、残件、次の必要consumerを短く記録する。
6. **Continue**：`SCOPED_PASS`なら依存する次Batchに進む。証拠不一致・安全境界の破損・権限越境は停止して原因を特定する。

### 5.1 既存能力の保存

- P2 Compare、P3 Handoff、P4〜P13、B0〜B4の有限受入れを後退させない。
- テスト件数・ファイル数を成果目標にしない。必要な正例・負例が不足するときだけ足す。
- 正本・履歴・監査・Fixtureの意味を、最新版への書換えという名目で消さない。過去FAILは当時FAILとして残す。
- 既存のRust Broker、Flutter Shell、各Adapter、`tooling/run_cargo_isolated.py`、テスト基盤、Conformanceを再利用する。全面リライトを工程の前提にしない。
- 有効な小さい差分を重ね、将来の拡張のためだけの抽象化・ダミー配線・説明不能な防御を作らない。

### 5.2 性能・資源・可用性

- Windowsの現行8GB級環境、OneDrive同期、WSL2競合、Broker／Agent process tree、実Provider呼出しを、観測可能な条件として保持する。
- OneDrive同期ディレクトリへRust・Flutter等の一時build出力を置かず、既存の分離Toolingを利用する。
- 計測は同一負荷・同一比較対象・失敗率・latency・memory・disk・後片付けで行う。最適化で権限・失敗の可視性を失わない。
- Resource／性能の主張は実測時点の範囲を超えて製品全域へ拡張しない。

## 6. 成果物の構成と採否記録

- 実装差分（関連要求ID・Producer／Consumer／OS付き）

**着手条件**：Ownerが本3点を採用し、Codexが最新`main`・`AGENTS.md`・正本を読み直すこと。

本工程表の発行それ自体は採用・実装・正式Releaseを意味しない。
