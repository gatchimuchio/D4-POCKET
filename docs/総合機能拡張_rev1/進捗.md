WindowsのC3経路を、登録済みMINIDORA Adapter、Rust Brokerの `RuntimeResourceRegistry`、通常認証済みIPCの `実行系資源観測`、Flutter Runtime Centerの「資源」tabへ接続した。queryは版と実行系IDだけを受け付け、Broker側でもASCIIの実行系ID形式を検査する。PID、endpoint、port、権限、承認、履歴長をUIまたはIPC payloadから受け取らない。画面は実行系IDを入力し、手動の「資源を更新」だけで観測を要求する。自動更新、PID入力、endpoint入力、ライフサイクル操作はC3に含めない。

登録時は明示 `127.0.0.1:port` のlistener所有PIDとprocess作成時刻を二段階で照合する。観測時も同一endpointの所有者をprocess読取の前・中間・返却直前に再照合し、登録PIDと作成時刻の組と一致した場合だけ `bound` / `LIVE_RUNTIME` を返す。listenerの消失、別processへの移動、PID再利用、endpoint再照合不能、作成時刻不一致は `binding_mismatch`、process読取不能は `exited` とし、PID、作成時刻、前回CPU sample、短期履歴を破棄する。失効後は全metricをunknown、短期履歴を空にし、再登録なしに別processへ追従しない。

Windowsで `bound` のとき、稼働時間、累積process CPU時間、CPU利用率、working set、private bytesを `LIVE_RUNTIME` として返す。CPU利用率は100ns単位のprocess CPU差分と高精度wall timeから計算し、初回、時間差不足、0〜100の範囲外、又は精度を安全に確保できない場合はunknownにする。Disk I/O、Network I/O、GPU利用率、VRAMは対応するprocess別collectorが未接続のため `INTERNAL_STATE` のunknownである。処理中要求数と失敗要求数だけはBroker内の現在集計を `INTERNAL_STATE` として返す。監査時刻は秒精度でありミリ秒応答時間の計測には使えないため、現在の `平均応答Millis` は常にunknownである。短期履歴のエラー率は失敗数÷完了数×100の小数として返し、完了数0、失敗数が完了数を超える、又は安全な数値精度を確保できない場合はunknownにする。

Windows開発hostでは、隔離した実MINIDORA child process、通常認証済みBroker IPC、Dart製品clientを使う `python tooling/minidora_live_check.py --reference C:/Users/mzcum/codex-work/MINIDORA-reference --dart-client` により、listener所有PIDがMINIDORA childと一致するbound観測、CPU/RAM、短期履歴、未対応metricのunknown、監査body hash結合を確認した。RustのWindows native collectorとBroker全試験、Schema/conformance、日本語厳格監査、Flutter client/UI試験と解析、`flutter build windows --debug` は開発検証として実行した。Windows画面検証は再開し、debug buildを隔離した実MINIDORA childとBrokerへ接続して、Runtime Centerの資源tabから実行系ID `left` を指定した。二回の手動更新で、`bound`、listener所有PID、`LIVE_RUNTIME` のCPU/RAM値、観測監査ID、2点の短期履歴を画面上で確認した。未接続のDisk I/O、Network I/O、GPU、VRAM、平均応答は、`INTERNAL_STATE` と理由付きの不明値として表示された。PID/endpoint入力、自動更新、ライフサイクル操作は表示・実行しなかった。検証専用のdesktop、Broker、child processは確認後に終了した。

## C4 実行系ライフサイクルの接続

C4では、開始、停止、再起動、一時停止、再開、隔離を、登録済みLifecycle Adapterだけへ到達するRust Brokerの統治経路として実装した。generic command dispatchは停止したままであり、通常資格経路は `実行系ライフサイクル状態`、`実行系ライフサイクル承認要求`、`実行系ライフサイクル操作` だけを受け付ける。`実行系ライフサイクル承認` はowner専用資格経路へ分離し、Flutterはowner資格、PID、endpoint、command、argv、環境変数を入力・保存・送信しない。BrokerEndpointは必須 `credential_role` で `normal` と `owner` を明示する。Desktopは完全な通常資格endpointだけ、owner CLIは完全なowner資格endpointだけを接続前に受理し、role欠落、未知値、余分field、逆roleを拒否する。

Brokerは各遷移時に、登録済みRuntime、Adapterが宣言するCapabilityと操作対応、現在のPermission、canonical payload hashに結合したowner Approval、RecoveryAction、durable audit/replay/session状態、現在のlifecycle stateを再照合する。いずれかが不成立ならAdapterを呼ばず状態を変えない。成功遷移は再観測された `LIVE_RUNTIME`、consumed Approval、外側IPC応答と一致するlifecycle監査IDを持つ。隔離はterminal stateであり、quarantine Adapter呼出し前に監査予約をappendできた直後、同じ実行系IDの通常対話Adapter、資源観測、作業領域root・承認・基準点を除去して通常操作と承認を空にする。Adapter失敗またはBroker停止後にも通常経路を復元せず、監査chainから検証して復元した隔離予約だけをBroker再起動後に維持する。破損した予約記録は過去の隔離を無視して再稼働させず起動を拒否する。

MINIDORA / BLUE-TANUKIの現行Adapterにはlifecycle Capabilityを追加していない。Capability不在は `not_supported` と空の操作・承認一覧を返すnegative caseである。C4の実接続と否定試験には、debug buildでだけ `--enable-development-lifecycle-fixture` を受け付ける隔離fixture Runtimeを用いた。release buildはこのflagを拒否し、fixtureは実運用Runtimeの権限やCapabilityを生成しない。

Flutter Runtime Centerには「ライフサイクル」tabを接続し、Brokerが返した状態、証拠種別、操作一覧、承認一覧だけを表示する。Rust childが通常IPC socketを継承しても応答をEOF待ちにしないよう、Desktop Broker clientは最大4 MiBの最初のJSON行を読取り、改行後に接続が開いたままでも応答を確定する。空行、改行なしEOF、上限超過、5秒timeoutはfail-closedにする。
