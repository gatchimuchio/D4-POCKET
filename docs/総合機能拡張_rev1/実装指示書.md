---

# 1. 命令

このtaskは調査・提案ではない。

添付仕様書と工程表の全機能を実装する。

一部だけ選択して終了してはならない。

---

# 2. 最重要原則

GUI-Shellを機能追加のために壊してはならない。

既存の、

```text
Authority
Permission
Approval
Audit
Recovery
Content Exposure
Adapter Boundary
Rust Security Broker
```

を全機能で維持する。

---

# 3. 日本語基底

最初に、

```text
規定/00_日本語基底規定.md
```

を読む。

新規GUI-Shell独自概念を英語から設計しない。

外部Protocol名、外部field名、既存識別子だけ原形保持する。

---

# 4. ローカルを基準とする作業（Local-first）

作業主体はローカル。

GitHub上を開発主体にしない。

毎単位:

```text
実装
試験
監査
commit
push
remote確認
```

まで閉じる。

---

# 5. GitHub CI禁止

自動CIを追加しない。

GitHub Actionsはローカルで不可能なOS build等の手動補助のみ。

原則 `workflow_dispatch`。

---

# 6. CI非使用の条件

CIがない分、Codex自身が全変更の試験を設計・実行する。

「testが存在しなかった」は試験省略理由にならない。

必要ならtestを追加する。

---

Baseline validationを実施。

---

# 8. 現在状態を正本として再確認

仕様書中のfile数、schema数、test数を固定値として信用しない。

作業時点のmainから再計測する。

古い文書の「未実装」を現在状態へそのまま適用しない。

---

# 9. 実装順序

工程表のC0→C34を基本順序とする。

ただし既存実装によって対象機能が既に部分成立している場合:

```text
再実装しない
↓
gapを特定
↓
最小差分で完成
```

---

# 10. 作業領域インスペクタ

Agent Centerを実運用可能にする。

必須:

```text
ファイルツリー
変更ファイル
差分
Tool履歴
shell履歴
test
Approval
Audit
rollback preview
```

workspace外やsecret pathを表示・操作経路から保護する。

---

# 11. 実行履歴

履歴はAuditの代替ではない。

Auditを変更せず、新実行要求を生成する。

---

# 12. 再実行・分岐

過去のPermission/Approvalを再利用しない。

必ず現在条件で再評価する。

---

# 13. 資源監視

Windowsで実測する。

CPU/RAM等はRuntime processへ正しく紐付ける。

取得不能値を0として表示しない。

unknownとする。

---

# 14. 実行系ライフサイクル（Runtime lifecycle）

Adapter Capabilityなしでstart/stop等を表示しない。

Broker経由のみ。

---

# 15. 評価ラボ

決定論評価を第一とする。

LLM評価をAuthorityやsecurity判定へ使わない。

---

# 16. 資格情報

秘密値をFlutterへ渡さない。

ログにも出さない。

error messageへ混入させない。

---

# 17. 外部道具接続（MCP）

MCPを便利な直接Tool実行shortcutとして実装しない。

必ずGUI-Shell Contractへ正規化する。

---

# 18. エージェント間接続（A2A）

外部Agentを信頼済みAgentとして自動登録しない。

Agent Cardは宣言にすぎない。

---

# 19. 観測とAudit

絶対に混同しない。

```text
Trace/Metric = operational observation
Audit = security/accountability evidence
```

---

# 20. 更新（Update）

既存Update Policyを再利用する。

別のupdate authorityを作らない。

---

# 21. 運用プロファイル（Profile）

Profile適用でPermissionを付与しない。

Profileは要求configurationのみ。

---

# 22. 複数Host管理（Multi Host）

Host単位でAuthority contextを分離する。

跨Host permission sharing禁止。

---

# 23. Adapter管理

Adapter install/remove等はすべてsensitive action。

UIからfilesystem直接変更禁止。

---

# 24. Windows優先（Windows-first）

現在の実機はWindowsのみ。

Windowsで可能な全実装・試験を止めずに進める。

```text
非Windows実機なし
≠
開発停止
```

---

# 25. macOS/iOSの補助検証

Windowsでsource/project/testを完成させる。

Macでしか証明できない範囲だけ未検証とする。

必要時は手動Actions。

---

# 26. Androidの開発と検証

実機検証凍結を守る。

凍結解除までADB接続を要求しない。

build/testは続行する。

---

# 27. 正式releaseの未成立条件（release blocker）

release blockerをdevelopment blockerとして扱わない。

外部条件待ちだけなら次機能へ進む。

---

# 28. GUI設計

画面を無制限に増やさない。

責任が既存画面に属する場合はその中へ統合する。

新規独立画面が必要か必ず責任分析する。

---

# 29. 性能（Performance）

resource polling、history、trace、searchによってUIをblockしない。

大規模履歴はpaginationまたはbounded loadingを使う。

---

# 30. 保存

無制限に履歴を保存しない。

保持期間、容量上限、rotationを設計する。

ただしAudit retentionとは別契約とする。

---

# 31. エラー処理（Error）

catchして無視しない。

最低:

```text
operator-readable message
technical detail
error code
recoverable
RecoveryAction
Audit
```

を必要に応じて提供。

---

# 32. 否定試験（Negative tests）

新規機能ごとにAuthority escalation試験を追加する。

最低共通:

```text
metadata authority injection
UI state authority injection
history authority reuse
profile permission escalation
MCP tool escalation
A2A agent escalation
cross-host permission reuse
credential leakage
notification action bypass
telemetry trusted-as-audit
```

---

# 33. 既存回帰

毎major block後、

```text
schema
conformance
日本語基底
Rust
Flutter shared

Mobile
```

を再検証する。

---

# 34. Windows実機試験

可能な範囲で実アプリを起動して確認。

fixtureのみでGUI完成を主張しない。

---

# 35. 長時間試験

新しい監視・履歴系実装後に必須。

resource leak、timer leak、socket leakを確認。

---

# 36. Git還元

意味の異なる変更を巨大commitへまとめない。

各完成単位でmainへ順次還元する。

push後remote HEAD一致を確認。

---

# 37. 文書

コード完成前に「implemented」と書かない。

実装・試験結果に基づいて更新。

# 39. 停止条件

以下以外ではowner質問待ちで止まらない。

* 秘密鍵owner操作
* 有料credential
* 正式配布identity
* 物理実機必須
* 法的/契約的owner判断
* 現行正本間に解消不能な矛盾

それ以外はRepositoryから判断して自律的に続行する。

---

# 40. 最終命令

目的は、

> 「機能が並んでいるGUI」

ではない。

> 「Runtime / Agent / Tool / Protocolを、安全境界を維持したまま日常運用できる総合Control Plane」

を完成させることである。

全機能を最後まで実装する。

非Windows実機の不在を理由に、Windowsで可能な実装・試験を停止してはならない。
