## 0. 目的・完成条件・現在位置

**AIがD4 Pocket経由で必要な実能力を使い、自分のTaskを遂行して結果を次の行為へ反映できること**が工程全体の主目的。D4 Pocketは能力の接続・実行・監督基盤、製品ユーザーは目的を指示して製品を使用する。管理GUIの完成やテスト件数を最終成果に置換しない。

工程の依存関係：

1. W00：既存要求・実装・証拠の対応を固定（既済）。
2. W01：通常Releaseの一件実Task（Windows/Codex CLI限定CLOSED）。
3. **W02：AI→実Tool→同AIへの帰還**（現在の最優先未成立）。
4. W03：異種RuntimeとAgent間の汎用実仕事。
5. W04／W05：実Capabilityの組合せ・追加・独立App化。
6. W06／W07：OS別一般製品の導入・操作・保全。
7. W08：緩衝の自己適用、全体QC、対象別QA、Release Review。

これは**能力の成立順序**である。複数工程を妨げない正本整合・検証器修復・保全は並走してよい。MVP、画面実装率、Schema数、旧局所CLOSEDを理由に全製品完成へ縮小・すり替えない。

## 1. Gateの原理と状態管理

- 各W Gateは **目的→実producer→実consumer→実結果→検証→Audit／Recovery** が成立した時だけ閉じる。装飾GUI・Manifests・Mock／fixtureは条件付き証拠。
- 現行状態は`PLANNED / IN_PROGRESS / SCOPED_PASS / CLOSED / BLOCKED / FAILED`と、原因分類`CODE_PRESENT / WIRED / BUILD_GAP / BLOCKED_AUTHORITY / EVIDENCE_MISSING`を併記する。`SCOPED_PASS`や`CLOSED`は対象OS・candidate・Runtime・modeが限定される。
- 旧W01の限定CLOSEDと新W02の未成立を混同しない。既存P0〜P13／B0〜B4等も同じ版・作用・consumer条件で保持する。
- 機能・安全・証拠・出荷のGateを分離し、`release_ready`や`supported`の表示は契約・実動・独立判断の必要条件が揃うまで変更しない。
- Safety Gateに失敗した場合は、その危険な機能を無効化して**他の独立施工を進める**。実装・試験に存在する危険そのものと、一般公開の可否を混同しない。

## 4. W03〜W05：AIの能力範囲を実際に拡張する工程

### 4.1 W03/G3：汎用性と実Handoff

1. Codex CLI固有のTask実装と共通Shell Core／Broker Contractを分離し、異種Adapterが必要な作用を同じ入口で消費できるようにする。
2. **異種Runtimeで実Task**を通し、Capability／Security／Result／Errorが共通語彙で保持されるか比較する。既存のMINIDORA HTTP Dialogueだけで実Task互換と宣言しない。
3. Agent間で目的・結果・context・diff・test・失敗を渡す。送信元のCredential／Permission／Approvalは移譲しない。
4. 外部A2AについてCard表示とTask／Message／Artifact／Streamの実対応を個別に検証し、未対応は`unsupported`とする。

### 4.2 W04/G4：Composeの実作用

1. 登録Runtime／Tool／Agent／Capabilityの実CatalogとManifest参照を照合し、出自・製品ユーザーの必要権限・依存・互換・不足を明示する。
2. 構成が選んだ実能力を利用して成果を出し、存在しない参照、未認可Capability、構成間の衝突を拒否する。
3. 表示上の候補と、実際に配線・build・installedで使用できる状態を別にする。

### 4.3 W05/G5：独立Appと検証済み拡張

1. Export Manifestを新AppのRuntime／Installerに**実消費**させる。安全CoreとApp／Audit identityは保持する。
2. Module選択と実行能力・除去能力を一致させる。binary pruning／容量／性能の改善は実測artifactに限り主張する。
3. **製品AIが拡張案を出す実行主体**、**施工者がその提案を独立審査・実装する役割**を分離。製品Runtimeの自己変更・自己承認を禁止し、製品品質・配布に関する最終判断は該当する責任者へ帰属させる。
4. 独立Appの初回、権限、更新、復旧へG5証拠を連結する。開発用Bundleの存在で製品完成とはしない。

## 7. 作業・品質・Gitの配置

1. **小単位**：原要求、現在HEAD、既存CLOSED、producer→consumer、必要な製品安全境界、次の実作用を再確認し、差分実装と局所検査を行う。
2. **BUILD_BATCH**：意味のあるconsumerを動かせた単位で必要なSchema／Conformance／Rust／Flutter／Manifest／日本語・安全検査を実施し、source・artifact・OS・試験条件に紐づく証拠を固定する。Gitの操作方法・施工者の権限は指示書に従う。
3. **BUILD_COVERED後**：全要求・OS別実物のQE_QC→QA→Release Reviewを実施。安全重大な負例・停止試験はBUILD中にも必要な時点で行う。
4. **判断責任の引継ぎ**：製品ユーザーの利用許可は製品契約、技術品質は施工・検証Gate、正式配布と最終GOは出荷責任者の判断で扱う。工程表には開発ツールの都度確認をGateとして置かない。
