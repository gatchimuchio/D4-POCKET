## 0. 主語と目的――全判断の最上位基準

**D4 Pocketの能力利用・仕事遂行の実行主体はAI／LLM／Agentである。** D4 Pocketは、AIが外部のソフトウェア・Runtime・Agent・Tool・Serviceを必要に応じて扱い、仕事を完遂する汎用的な身体・能力実行基盤である。製品の**使用者は人間のユーザー**。AIを製品の使用者と混同せず、「能力を実行する主体」として独立に扱う。

### 0.1 五つの役割を同一視しない

| 役割 | 定義 | 本書での適用 |
|---|---|---|
| **設計者** | 仕様・構造・成立条件を設計する者 | 製品契約・能力接続・安全境界を定義する |
| **指示者** | 目的・要求・制約を与える者 | 製品利用時はユーザーがAIへ達成目的を指示する |
| **施工者** | 設計・指示に従い実装・検証する者 | 製品を構築する開発担当。製品実行時のAIと同一ではない |
| **使用者** | 完成した製品を利用する者 | D4 Pocketのユーザー。許されたCapabilityをAIへ利用させ、結果を受け取る |
| **責任者** | 対象となる判断・結果に対する責任を負う者 | 製品品質・出荷、利用時の許可・操作など**責任対象ごとに特定**する |

同一人物が複数の役割を兼ねることはあるが、**役割・権限・判断を合算しない**。例えば製品ユーザーは通常「指示者」と「使用者」を兼ねる。一方、製品品質・出荷の責任は製品側の責任者が負い、ユーザーへ自動転嫁しない。製品RuntimeのAIは上記五役の曖昧な代用品ではなく、目的達成の**実行主体**である。施工者Codexへの開発委任と確認は本書の製品役割表へ混入させない。

**同名の区別**：本書でいう`Codex CLI`はD4 Pocketに接続される**製品側のAI Runtime**を指す。D4 Pocketを実装・検査する**開発施工者としてのCodex**とは別の役割・セッション・権限であり、前者に後者の施工委任を流用しない。

目標状態は、一般利用者が導入したD4 Pocketで、AIが必要なソフトウェア能力を実在確認し、許可された作用を行い、結果を評価して次の作用に反映し、最終成果・失敗・検査・監査・回復可能な状態を保持できること。Capabilityを追加・組合せ・構成し、別の独立Appとして利用できることも製品要求に含める。完成範囲をMVPへ縮小しない。

**主目的の成立連鎖：** `ユーザーの目的・許可範囲 → AIのTask・能力要求 → 実Capability発見・照合 → Brokerの認可検査 → 元Tool／Runtimeの実作用 → 実結果 → 検査 → AIへの結果帰還 → 次の意思決定・完了／停止／復旧 → 再利用・構成・拡張`。

GUIはユーザーによる観測・必要な権限設定・停止・復旧の表現面であり、AIが能力を使うための必須手操作連鎖ではない。ユーザーの許可境界を保ったまま、AIの能力要求から次の結果消費までをUI非依存の共通Contractで接続する。UIが存在すること、手動ボタンでToolが1回動くこと、Schema／Mockが通ることは主目的の達成を意味しない。

## 3. 変更不可の責任・安全境界

| レイヤー | 担当と入出力 | 越境禁止 |
|---|---|---|
| AI／Agent | 目的解釈・能力要求・結果に基づく継続／停止 | 自己承認、ユーザー資格の偽装、Tool結果の権限化 |
| Adapter／MCP／A2A／Provider | 個別Protocolを共通Task／Capability／Resultへ正規化 | metadataから信頼・Permissionを生成、無条件fallback |
| Shell Core／Contract | Runtime・Task・Session・Workspace・Capability・受入条件の統一 | 特定Agent前提への固定、UIへ権限責任を委譲 |
| **Rust Security Broker** | 認証IPC、Permission／Approval、Credential、作用、Audit、Recovery | AuthorityをFlutter／Python／Agent／Manifestへ移譲 |
| Flutter Desktop／Mobile | ユーザーの状態観測・許可・停止・問題・復旧・構成選択 | UI内部で認可を生成、秘密を保持、Headless使用を妨害 |
| Export App／配布 | 構成を実行可能な独立artifactへ変換し導入・更新・復旧 | Manifestを実作用・署名・installed保証として扱うこと |

安全の共通Contractは`Capability → Permission → Approval → AuditEvent → RecoveryAction`、Content Exposureの`none / hash_only / summary / redacted / full`、Workspace／Host分離、Credential・秘密、非冪等作用のreplay拒否、process tree cleanup、source/artifact/OS同一性を維持する。ユーザーの有効な権限がなければ対象の実作用だけをfail-closedとし、無関係な製品操作・安全な表示まで一律停止しない。

## 4. 製品利用者の目的・許可・責任境界

この節は**D4 Pocketを実際に利用するユーザーと、能力を実行するAIとの製品内契約**だけを定める。Codexの開発操作、Computer Useの外部規則、開発指示者への施工確認は扱わない。

1. **目的の入力**：製品ユーザーがAIへ達成目的・制約を指示する。AIは利用可能なCapabilityを発見・選択し、実行計画と必要な作用を構成する。
2. **利用範囲の指定**：ユーザーはWorkspace、対象Service／Tool、操作種別、秘密の扱い、期間等を必要に応じ指定・変更できる。許可範囲はBrokerが保持・再評価し、UI表示やAIの文章だけでは拡張しない。
3. **確認の発生条件**：有効な許可・事前に設定された条件内なら、AIの各内部ステップへ一律の画面確認を要求しない。新しいScopeや重大・不可逆な作用など、製品契約が追加のユーザー意思を要求する場合だけ対象を明示して確認する。
4. **権限不足と失効**：Permission／Approvalが不足・失効した対象作用は拒否する。AIは代替の適法な手順を提案・選択できるが、権限の自己生成、拒否された作用の迂回、非冪等作用の無条件再送はしない。
5. **記録と責任**：許可の指示・scope・主体・結果・失敗・Auditを対応付け、ユーザーが確認・停止・復旧できる。ユーザーの利用上の判断と、設計者／施工者／出荷責任者の製品品質責任を混ぜない。

ユーザーの操作性を理由に安全側境界を省略せず、安全性を口実に不要な確認を大量発生させない。実際の確認条件は契約と検査可能な作用に基づき決める。

| ID | 目的に必要な実能力・実consumer | 完了に必要な証拠と保持条件 |
|---|---|---|
| **N01 Task実仕事** | 通常製品でAIが目標→Task→元Tool作用→結果→検査→終了／復旧を完遂 | Windows Codex CLIのW01/G1局所CLOSEDを保持。他Runtime・OS・installedの合格へ拡張しない。秘密／Workspace負例、再起動、実結果照合を追加検証 |
| **N02 AI→Tool→AI** | AIが実Catalogから能力を発見・選択し、Broker認可を経てMCP Toolを使用、未信頼結果を判断材料として継続する。**GUIがToolと後続Taskの進行責任を持たない** | 同一artifact／Agent／Sessionで結果に依存する後続作用が変化するG2。製品ユーザーの必要なApprovalは独立、fresh Permission、replay／secret／fault負例、Audit相関を確認 |
| **N03 異種Runtime** | 特定CLI実装ではなく複数の独立AI Runtime／Providerが共通Task・Capability・Result契約を消費 | 2種類以上の実Runtimeで同一契約による実Task。未対応能力は明示`unsupported`、CredentialはBroker境界で保護 |
| **N04 Agent間Handoff／A2A** | 成果・context・diff・失敗・検査を別Agentへ引継ぎ、外部A2A実Task／Message／Artifact等へ接続 | P2/P3局所CLOSEDを維持。実相手／版／作用ごとに本番交換、権限・Credentialを引き継がない |
| **N05 能力発見／Compose** | 実在Catalogの互換性・依存・不足を検証し、許可された組合せが動作する | `manifest_only`と`wired/build_verified/installed_verified`を明確に分離。存在しない能力の拒否、実Compose後の元作用 |
| **N06 独立App／Module** | 構成を独立Runtime／Installerが消費。選択Moduleが働き、不要Moduleが除外される | App/Audit identity、source・artifact hash、installed実行、最低安全Core維持、binary pruningと資源は実測のみ主張 |
| **N07 AI拡張** | 製品AIは能力提案・契約・差分を生成し、独立した開発審査・検証・導入へ引継ぐ | `proposal_only`を正直に保持。独立した施工者の審査・検証を通す。Runtimeによる自己採用・自己改変・自己承認は不可 |
| **N08 緩衝／干渉調停** | OneDrive、WSL、TLS、SAC、process、OS差などの実行干渉を合法的に制御・復旧 | B5の根因・作用・副作用を同条件実測、B6結合QCへ。元Task成功条件とBUF試験IDを混同しない |
| **N09 ユーザー製品UX** | AIの実Task、能力使用、許可待ち、結果／差分、問題、復旧を製品ユーザーが理解・操作できる | 画面個数でなく同一実Taskから作用・証拠へ辿れる。UIハングと応答性を解消。ユーザーの必要な認可をAIの自動判断へ混ぜない |
| **N10 OS／配布** | Windowsを先行し、Linux native／macOS DesktopとAndroid／iOSをそれぞれ製品化 | OS固有の通常installed、Broker、権限、更新／rollback、uninstall、署名状態・配布証拠。物理環境のない対象は未観測 |
| **N11 証拠とGate** | 旧P/B/Q、全N／W／Blockerを要求→producer→consumer→OS→test→source SHA→artifactまで結合 | 通常Gateの構造PASSをRelease PASSに誤用しない。W02〜W08の必須consumer状態がStrict Release Gateで無条件に検査できること |

## 6. 統合受入れ条件

1. **AI主体G2**：実AgentがTool能力を見つけ、要求を発し、ユーザーから付与された有効な利用権限をBrokerが検査したうえでToolを実行し、結果を次のAgent作用で実消費する。UIは必要な許可・観測に使えるが二段階の手動ボタン操作を必須にしない。Headlessや異種Runtimeが同一Broker Contractを利用可能。
2. **実仕事・安全**：実Tool作用、Workspace内成果、出力の独立照合、Permission拒否・取消・期限・replay・異常応答・crash後のcleanupを、同一候補・Audit相関で再現。非冪等作用を盲目的に再送しない。
3. **汎用性**：独立した2種類以上のRuntimeをAI能力利用主体として交換可能にし、対応差・接続不能を正しく示す。A2A実交換と権限分離を個別に受け入れる。
4. **構成・App化**：実Catalog→Compose→選択機能の実作用→独立artifactでの同一能力→更新・復旧まで証拠を結合。Manifestだけでは不合格。
5. **製品UI・OS**：通常インストール済みのWindows候補で初回起動→Broker→AI Task→Tool→Audit→Recovery→更新・撤去を追跡。他OSは独立の実機証拠で判定。
6. **完全性**：rev5全要求とN01〜N11の必須consumerが`BUILD_COVERED`、同一候補のQE_QC・QE_QAとRelease Blockerを閉じる。最後の出荷責任者によるFinal GOは技術結果から自動生成しない。

受入れ記録は`LIVE_PRODUCT / LIVE_RUNTIME / FIXTURE / CONFIG / NOT_RUN`を区別する。正常例・拒否例・障害・復旧・OS／source／artifactの射程を必ず併記する。歴史的なCLOSEDは同一条件を満たす限り証拠を再利用できる。

## 7. 品質体系とReleaseの責任

`QE_DESIGN → QE_BUILD → SYSTEM_SHAPED → BUILD_COVERED → QE_QC → QE_QA → QE_RELEASE_REVIEW`を継承する。BUILD中は意味あるconsumerを前進させ、各小単位で全suiteや全QAを反復しない。ただしAuthority・秘密・復旧の変更は変更時に安全試験を行い、不成立なら対象経路を停止・隔離する。BUILD_COVERED後の全体QC、正式Q0〜Q7、対象別QA、配布資格・署名・出荷責任者のGOを別状態として保持する。

`release_ready=true`や未対応Capabilityの`supported`化は、実作用証拠・Release Gate・必要な責任者の決裁が成立した場合だけ許す。既存Quality GateのFAILを、対象集合の恣意的縮小や試験器の無言の緩和で隠さない。禁止事項のための停止も**作用単位**とし、別に完成できる工程まで全面停止しない。
