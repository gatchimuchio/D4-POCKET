## 1. 命令の目的とQCの対象

D4Pocket開発で累積したすべてのボトルネックを全数調査し、共通するソフトウェア間の干渉の原理を解明して、エージェントが毎回対処せずに済む**下位緩衝基盤**をD4Pocketの汎用機能として成立させる。汎用性はRust/Flutter/Windows等だけに限定しない。

**診断・エラー分類・画面報告を作ることが目的ではない。** 互換変換、隔離、環境再構成、状態調停など実際の作用が、元の要求を保ったまま上位処理を成立させたかを確認する。

最初に「何が吸収できるか」だけを選んで対象範囲を減らさない。全ボトルネックを調査対象に登録し、事実・根因・吸収試行・残余を記録する。ただしOSやSecurityを突破してまで自動吸収したと偽装しない。

**QCとして扱う範囲**：構想・要求の妥当性、設計の関係と干渉、既存の責任境界、実装と接続の整合、試験方法の適否、実物の挙動、是正効果、既存正常系への副作用、下流への障害移送、実機・配布後の状態。これらを開発途中から検査する。『B0〜B6を作ってからQAで品質を考える』という施工を禁止する。

**受入の責任**：品質状態は実観測に照らして判断し、local QCで要求を閉じたこと、統合QCで製品が要求を満たしたこと、正式ReleaseをOwnerが承認したことを別々に記録する。

## 4. 原理確定（B1：設計QC）

- 独立した言語/OS/tool/API/実行基盤の間で、どんな干渉がどう生成され、何の操作で吸収されるか、要求原文から日本語で定義する。

- 既存の構成を単純化して境界衝突を減らす案、緩衝hubで動的に調停する案、toolchain既存機能を再利用する案を比較し、根拠のある責任分割だけ採用する。

- **QCの上流帰還を設計に含める。** 失敗したときの修正点は必ずしも緩衝コードではない。要求の矛盾、Adapter契約の誤認、検査環境の差、試験器の誤検出が原因なら、それぞれ責任を持つ位置まで戻り、同等性と副作用を再評価する。

## 5. 各作業単位の施工QC（B2–B6）

**1タスク1指示書。** 施工開始ごとに現行HEAD・適用正本・担当機能・対象ファイル・受入試験を定める。1件が閉じる前に無関係な仕様・コードへ広がらない。外部で過去にCLOSEDになった部分を「強化」のためだけに開かない。

**施工単位では、品質管理を実装の後へ置かない。** まず、要求と不成立条件の妥当性を見てから、どの機構を変更するべきかを選ぶ。設計・契約・実装・試験のどこに原因があっても必要な位置まで戻る。

必須の順序：

```text
要求の原文・目的・成立条件・不成立条件のQC
→ 現行の実物／証拠・失敗原因の観測と反証
→ 日本語意味正本、設計候補・責任境界のQC
→ Contract/Schemaと正常・否定ConformanceのQC
→ 最小の実作用を施工し、その変更自体のQC
→ 元Toolchainで介入前後の実挙動・意味同等性を比較
→ 副作用・下流への問題移送・既存安全回帰のQC
→ 不一致なら原因と必要な上流まで帰還し、再設計/再施工/再試験
→ 当該単位の局所QC受入（未解決と証拠範囲も固定）
→ commit / push / remote HEAD・backup照合（明示許可済み作業のみ）
```

### 技術的な成立条件

- 実装はすべて「Agent→既存Broker認可→緩衝実作用→元Toolchain→独立検証」の実経路へ接続する。新しい権限源は作らない。
- toolchain/Host/Workspaceの入力変更は、元入力の同一性を照合しても無条件に安全なものではない。明示許可のないfile/lockfile/credential/registry/OS保護変更をしない。
- B0で得た全ての原因行を、既存または新設の共通緩衝機構・本来の設計是正・実験と検証へ結び付ける。未成立・未知は未閉包のまま保持し、**実証した吸収不能**と安易に混同しない。全件の調査対応を全件解消の証拠へ昇格させない。
- 変換が元の機能・試験・仕様の意味を損ねる場合は適用を拒否する。テストの削除/緩和、失敗のexit code変更、障害の隠蔽、無制限retry、無断OS保護解除は禁止。
- UIは表示だけで、Permission/Approvalの生成源でない。既存Setup Doctorは読取り専用環境診断の責任を維持する。
- 外部ToolやAdapterをむやみに信頼せず、結果の取得元・出所・証拠classを保持する。未知はUNKNOWN。

## 7. QCの継続運用と既存Q0〜Q7の整合

### 7.1 QCは最初から稼働している

- **P13以前と進行中**：構想・実装・個別Acceptanceを含め既にQCで開発している。`PRODUCT_BUILD_MODE`は品質管理の不在を意味しない。既存文書上の`Final QA=DEFERRED`は**正式なQ0〜Q7検査の開始待ち**を意味し、QC自体の延期ではない。

## 9. Git/全期間QC手順（明示の施工委任があった場合のみ）

- 既存`AGENTS.md`のdirect-main、local-firstを維持。通常のfeature branch/PR、自動CIは禁止。手動GitHub Actionsは`workflow_dispatch`による必要なOS補助のみに限る。
- 編集前にfetch/prune・main clean/remote一致、local 2世代backupをrotateしremote tagとして保存。作業単位の実装・必要なlocal検証後にのみcommit/pushし、remote HEADとbackup ref/hash、working tree cleanを確認する。
- 既存Codexの別工程と競合するなら**編集前に中止**し、既存作業を巻き戻さない。
- 秘密値、build生成物、環境内private evidenceをRepoへ入れない。正本索引や公開内容に非公開設計を混入させない。
- 見つかった元不具合の設計修正が、別ownerのrepo変更を必要とする場合はそのownerの明示許可を得るまで行わない。
- 設計・実装・局所試験の間にQCを逐次行い、局所検証に成功していない単位をcommit/push完了として報告しない。テスト報告だけでなく実作用・下流干渉・再試験結果を含める。

## 11. B0単位の開始指示（採用後の第一QC作業の雛形）

**目的：** 現行P13完了済み製品の一切の変更を行わず、全ボトルネックの観測母集団と既存緩衝可能性を確定する。

**B0の出力：** 過去記録・code・tests・source commitへ結び付いた全事象台帳、構想・要求・設計の欠陥を含む原因/干渉構造、既存資産重複監査、未取得と未知、rev5原本との逐条照合表。**B0でQC観測が成立しても緩衝実作用が成立したとは主張せず、B1以降の言語・配置・詳細構成を先に決定しない。**

**B0停止条件：** (a) 現行P13未完了、(b) 最新原本欠落で整合主張できない、(c) 現行作業treeに競合、(d) 補遺が未承認、(e) 必要な証拠を取得せず全数と推定しそうになる、のいずれか。該当時は正確な停止理由を報告。

以後、B1、B2…の作業は別々の有限指示書として施工する。**本マスター指示書があるからといって、自動的に最後まで実行してよいわけではない。**
