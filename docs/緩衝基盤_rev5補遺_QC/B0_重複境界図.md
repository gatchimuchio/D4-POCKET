## 責任境界の見取り図

```text
要求・意味正本 / Product contract
        │ 何を成立させるか、どの失敗が不適合か
        ▼
実装（Rust Broker / Flutter UI / Adapter / native OS layer）
        │ 実行結果・error code・state transition
        ▼
test / UI automation / workflow harness
        │ assertion・test setup・polling・timeout・署名設定
        ▼
OS / SDK / toolchain / runner environment
        │ API availability・entitlement・filesystem / emulator state
        ▼
artifact / log retention / evidence index
          取得可能範囲と欠測。失敗の発生層とは別の証拠保存境界
```

`run`が赤いことだけから製品欠陥を結論しない。同様に、`test assertion failure`だから製品側の問題が絶対ないとも推論しない。対象`source SHA`と当該`test`の期待条件、実動作、後続修正・`PASS`を一組にして分類する。

## `B0`から後工程への引渡し

- 根因が実装/`contract`に属するか、`test harness` / `environment`に属するか、上流要求に属するかを分離する。
- 将来の「緩衝候補」は分類だけを残し、機構・配置・自動修復をここで設計しない（`B1 scope`）。
- `log`や`run`参照が欠ける行は[不足証拠一覧](B0_不足証拠一覧.md)の`ID`を維持し、類似`source SHA`や`step label`から閉鎖しない。
- `P13`閉鎖条件、`task_execution=unsupported`、`release_ready=false`、`Final QA DEFERRED`はこの図で変更しない。
