### 0.1 QCと既存文書の名称境界

- **QC思想**：本開発に採用する品質管理の考え方。品質を文書・宣言・保証表現から導出せず、対象の実体と作用に対する観測・是正・再試験で成立させる。最終検査もQCの一部分にすぎない。
- **局所QC**：各要求・設計・実装・接続・修正単位で、成立条件・反例・安全境界・結果・不適合の処理を閉じる作業。機能の『完成』と製品全体の『完成』は分ける。

- **受入・出荷判断**：局所QCでの要求成立、統合QCでの製品全体の適合、Ownerによる正式公開判断は別状態。同一人物が担当しても役割を混同しない。

### 0.2 QCの循環と上流再評価

```text
目的・要求の定義（何を成立させるか）
  → 成立条件・不成立条件の設定
  → 設計・既存機構との照合
  → 実装・統合・緩衝の実作用
  → 実物／実経路の観測・試験

```

後段試験だけをQCとして扱うこと、Test PASS数を品質そのものへ読み替えること、未観測を『保証できた』と表現することを禁止する。品質は実体の成立状態に対する判断であり、工程名では決まらない。

## 1. 目的、対象、思想の確定

### 1.1 解決したい構造

既存の開発では、Cargo/Rust・Flutter/Dart・Swift/Apple・Gradle/Android・Windows/macOS/Linux・実行系・検査系・配布系の境界を跨ぐたびに、依存関係、互換性、ファイルシステム、操作権限、ツール・環境状態の差異が顕在化し、上位エージェントが再調査・再構成・再試行を反復する。**この反復を生み出す境界そのものを緩衝する**。

ただし最初から「依存関係エラー」だけを母集団にしない。構想の前提誤り、設計責任の重複、契約不整合、実装の依存連鎖、試験環境の不再現、出荷証拠の断絶、過剰な修正反復など、D4Pocket開発を実際に阻害した全事象をQCの観測対象とする。その中から、下位緩衝によって制御できる生成構造を抽出する。単に『これは工程管理だから対象外』という先回りの切捨てはしない。

### 1.2 目的条件

- **BUF-R01 全件入力：** D4Pocket開発で確認可能な全ボトルネックを、期間・証拠源・実行対象を明示した母集団から取りこぼしなく台帳化し、解消・継続・不明を追跡する。新しい失敗も継続登録する。
- **BUF-R02 吸収主体：** 互換な変換、隔離、状態調停、実行接続の再構成、資源整理など、成立が証明できる下位操作は緩衝基盤が担う。エージェントへの失敗報告は主体機能ではない。
- **BUF-R03 汎用性：** 特定言語、OS、D4Pocket固有の既知エラー一覧へのハードコードで設計を閉じない。新しい依存や外部ツールを共通責任モデルで扱えるようにする。
- **BUF-R04 意味保持：** 調停前後で上位の要求・結果・権限・成功条件の意味を変えない。変換が意味を変える、または同等性が証明できない場合は勝手に適用しない。
- **BUF-R05 境界保持：** 既存Rust Brokerが所有するAuthority、Permission、Approval、Audit、Recovery、Content Exposure、Host/Workspace束縛を維持する。緩衝処理の成功は実行権限にならない。
- **BUF-R06 障害伝播抑制：** 同一原因の反復調査・人手介入・場当たり修正を削減する。失敗を不可視化、成功に偽装、単体retry PASSで根因閉鎖することは禁止。
- **BUF-R07 自己適用：** D4Pocket本体の実際の開発・検査経路を最初の包括的受入対象とする。過去の失敗履歴と、同条件の新規検証を区別する。
- **BUF-R08 QC一貫性：** 構想・仕様・設計・実装・試験・是正・配布まで、すべての作業で品質の成立条件と検証・修正の責任を持つ。『実装工程は品質管理の外』『Q0開始後に初めて品質管理』という扱いを禁止する。
- **BUF-R09 原因への帰還：** 品質上の不適合を受けたとき、事後報告や機械的なretryだけで閉じず、必要に応じて目的・モデル・境界・設計・検査方法まで戻して原因を是正する。修正の影響を再観測し、元の問題が別の境界へ転移した場合は未解決のまま管理する。

**「全件対象」≠「全件が技術的に自動吸収可能と証明済み」。** 全件を調査・設計・検証対象に置き、不可変のOS保護、本人操作、意味非互換などは吸収不能原因と残余を明示する。最初から対象から除外しない。

## 2. 基本原理：緩衝とは何か

緩衝は「エラーコードを共通化して返すこと」ではない。独立したソフトウェア境界A/Bが要求する前提が衝突しても、上位の目的を維持する**実行可能な媒介関係**を生成・適用することである。

```text
AIエージェント（目的／作業要求。権限源ではない）
    │
    ▼
既存D4Pocket Agent Task・Runtime Adapter・Rust Broker（既存権限判定）
    │  許可済み作用と現在のHost／Workspace境界
    ▼
【ソフトウェア緩衝基盤（追加対象）】
    ① 差異の観測・成立条件の組立
    ② 互換・競合関係の解決方針生成
    ③ 意味保持を確認した調停を適用（必要な操作は既存Broker経由）
    ④ 隔離した実行環境で本来のツールを実行・再検証
    ⑤ 成否・残余・再利用可能な根拠を上位へ戻す
    │
    ▼
既存OS／言語／Toolchain／Library／Network／Filesystem／製品試験
```

標準経路では**先に調停し、成立する実行へ接続**する。単に事後のエラーを分類する経路は緩衝の本体ではない。

### 2.1 介入手段の候補（採否未確定）

1. **入出力整合：** Schema、API、プロトコル、パス・文字コード・改行形式などの差を、変換規則と往復検証が成立する範囲で相互変換する。
2. **依存干渉隔離：** toolchain/version/ABIの競合を、同一Host内の限定コンテキスト分離または別Hostへの明示実行で解消する。lockfile/依存を無断更新しない。
3. **環境再構成：** 合法・許可済みの実行場所、artifact staging、cache再生成、出力先分離、toolchain固定を、入力hashとHost条件を保持して実施する。
4. **状態・寿命調停：** process起動順、port/listener衝突、終了・cleanup、stale lock、transaction境界を、実状態の観測に基づき復旧可能な経路へ戻す。
5. **失敗局所化：** 未成立な境界を特定し、影響をその境界に閉じ込める。根因不明の接続断やfalse PASSを「吸収した」ことにしない。
6. **適応・再利用：** 既に検証された変換とHost条件を照合し、同等条件なら再利用する。新条件での転用は再検証する。

上記は**採用候補**であり既存実装の存在を主張しない。別のpackage manager、専用shell、専用permission engine等を先に作ることを要求しない。

### 2.2 QCが緩衝作用を制御する条件

緩衝作用の実行前に、要求意味・許可・実行対象・可逆性・介入の期待効果を定義する。実行後には原操作の出力、異常残存、負の副作用、時間と資源の追加費用を照合する。合わなければ「緩衝成功」ではなく原因調査へ帰還する。

QCが制御する対象は、修復前の障害だけではない。**誤変換・誤隔離・別工程への障害移送・無駄な再試行・既存正常系の劣化**も、緩衝基盤が新たに作り得る欠陥として同じ基準で検査する。監査のPASS件数や手順の完了は効果の代用品ではない。

## 4. 責任の分割と接続先（暫定、B1で実コードと再照合）

| 責任 | 原則上の所有先 | 禁止事項 |

| ツール固有の適用 | 既存Adapterと、必要に応じた限定Host側実行主体 | 未承認コマンド・ネットワーク・資格の無断実行 |

### 4.1 QC責任の配置

QCは新しい特権サーバ、判定役、Approval機能ではない。既存の実行・状態・証拠を所有する各層に**検査可能な品質成立条件**を要求する規律である。緩衝基盤の非権限計算コアも、入力正当性・出力意味・効果・失敗の統治された実経路を持たなければならない。最終的な採否は、対象要求とOwnerの判断境界に従う。

## 5. 操作意味と必要契約（実装名・キーは仮称）

### 5.1 緩衝の処理系列

`要求受理（既存権限確認）→ 依存・環境・境界の実測 → 衝突関係の構成 → 解決候補の比較 → 意味同等性と権限の検査 → 許可された調停の適用 → 元のToolchainによる実実行 → 成果と根拠の照合 → 永続可能な範囲の結果登録 → 次回再利用`。

**成功条件は実行の成立であり、「READYを返した」「エラーを分類した」ではない。** 適用できない・未知の条件は保存して影響を閉じ込めるが、無根拠な成功は返さない。

### 5.2 新規契約に要求する要素（概念モデル）

- **緩衝要求：** 発行元Task/Runtime、Host/Workspace現在識別、要求された操作と制約、入力対象の固定点、元の目的・終了条件、依存拘束。
- **干渉関係：** 境界A・B、必要条件の出所、矛盾する値・依存辺、影響する操作、実測／推論／未知。
- **緩衝計画：** 可能な変換・隔離・調停作用の列、適用範囲、意味保持の検査、必要権限、失敗時の巻戻し、実行前の再照合条件。
- **適用結果：** 元のToolchainの実結果、調停前後の差分、独立確認、変更source/artifact hash、権限消費証拠、未解決の残余、環境固有の限界。
- **再利用条件：** toolchain/ABI/platform/Host identity/Workspace固定点、入力hash、規則版、取得時刻、有効期間、適用済み後の再観測。

完全なrawエラー本文・資格・秘密pathは既存Content Exposure規則なしに公開しない。検査用の必要な生証拠は保護領域に保持し、表層には証拠参照と構造化した機械識別を出す。

**QC情報の必須結合**：元要求IDと受入条件、緩衝前の観測、設計した介入、実際に適用した作用、介入後の観測、独立した再試験、結果に対する判断、残存不適合、次回再開放条件を同じ作業単位として追跡する。これは報告画面を緩衝基盤の本体にする意味ではない。

### 5.3 判定と実行を混同しない

- `整合候補あり`：変換を提案できる段階。実行許可でも成功でもない。
- `適用可能`：対象の現在条件と既存権限の確認を経た段階。元のTool実行成功ではない。
- `吸収成立`：調停後に元の要求が指定された同等条件で実行・照合された段階。
- `未成立`：条件違反・副作用・不明・外部制約など、検証可能な理由と残余がある段階。
- `未観測`：必要な実行条件が測れず、結果は確定できない段階。

どの状態もBroker permission/approvalやrelease-readyへ自動変換しない。実際の名称・JSON schemaはB1で日本語から決める。

## 6. 最初に検証する実問題

- **Rust/Flutter横断Build：** lockfile拘束とversion環境の下で、ビルド生成物を安全に分離し、source同一性を照合した上でエラー回避の可否を実実行で確認する。検査environmentとinstalled環境を混同しない。
- **OneDrive上の生成物・キャッシュ：** 失敗を出力先分離で吸収するなら、元sourceへの無断変更0、生成物のhash、再現性、失敗前後のcache/path状態まで確認する。見かけだけASCIIへ移すことを無条件の製品保証にしない。
- **Loopback/TLS fixture：** `FQ-TEST-LOOPBACK`の複数経路を再現し、listener寿命・切断タイミング・並行性・socket所有を実測した上で、具体的な干渉を消去できるか検査。単独再試験成功を吸収成立にしない。
- **Windows実行保護：** Smart App Controlなどを無効化しない。許可された署名・配布・実行条件がなければ未成立にし、無断の別実行経路を作らない。
- **クロスプラットフォーム：** Mac App Sandbox・Keychain・iOS Simulator・Android emulator/実機等、OSの正当な拒否はそのまま保持。OS間の同等性は実環境別に証明する。

## 7. 安全・仕様保全の不変条件

1. 失敗したcommandのexit codeを0へ変える、テストのassertionを消す、CI/test結果を隠す、警告を成功として握りつぶす操作をしない。
2. ロックファイル、依存の版、source tree、成果物を勝手に変更しない。変更する場合は既存Authority/Permission/Approval経路を再評価する。
3. Smart App Control、Gatekeeper、App Sandbox、OS Credential Storage、署名、Trust、TLSなどの保護を無断で停止・迂回しない。
4. 作業前後でHost・Workspace・current source・artifactの同一性を検証し、TOCTOU・symlink/hardlink/aliasや別HostへのAuthority持出しを拒否する。
5. 既存Test／Conformance／監査/Recoveryの意味を保ち、失敗の過去証拠を削除しない。
6. 新しいWrapper/shimを導入する場合は、元失敗、責任、nativeで不足する理由、同等性、削除条件まで明記する（AGENTS §8）。単なる「エラーを隠すWrapper」を禁止する。
7. Agent、memory、履歴、ログ、診断、metadataをAuthority sourceにしない。
8. 機械が内部処理を済ませても、その効果が依存先まで伝播していなければ成功扱いしない。
9. 内容露出とAuditが失敗した場合は、通常処理を安全に停止し、失敗を隠して継続しない。
10. 日本語意味正本を先に作り、既存互換識別子・他言語APIを必要最小限で保持する。非公開HDS内部原理を公開Repoへ混入させない。

## 8. QC判定・反証・測定（開発の全期間）

### 8.1 「緩衝成立」の受入れ式

ある干渉群に対し、(A) 失敗環境が観測され、(B) 緩衝の具体的な介入が同一入力・許可・要求意味を保ち、(C) 本来の上位操作が再試験で実際に成立し、(D) 適用前後の原因・変更・副作用・証拠が保持され、(E) 負例で未成立を正しく拒否できたときだけ、その**条件付き**吸収成立を主張できる。

旧失敗の削除、コマンドの成功偽装、単純retry、別Hostで一度成功しただけ、自己申告の成功は反証対象。障害が別工程へ転移した場合も解消ではない。

### 8.2 測定値（目標数値はBaseline測定後に採否）

- 同一要求の完了に必要な境界調整回数、再調査回数、修正再実行回数
- 吸収できた干渉原因の個数と、未吸収／未知／再発の原因の個数（母集団を明示）
- 上位エージェントへ委ねた判断数と人手介入数
- 同一host/commit/toolchain条件での総経過・CPU/RAM/disk/handle/process負荷
- 誤吸収率、正常経路の劣化、権限不正成立の有無、結果の意味同等性

指標数値を先に決めてPASSを演出しない。改善は条件一致の比較と失敗の残存を含む証拠で判断する。

## 9. rev5の検査工程と全期間QCの整合（既存Q0–Q7は改名・消去しない）

### 9.1 工程名とQC思想の分離

既存`docs/FINAL_QA_QUEUE.md`の表題・`Q0〜Q7`・`FQ-*`は、履歴と自動検査・進捗参照の識別子としてそのまま使う。本書では、これらの作業を**最終統合QCの検査段階**として位置付ける。旧称に合わせて開発全体をQA思想へ組み替えない。

**P13までのProduct BuildもQCの実行中である。** 構想・設計・実装・製品Acceptanceの各作業でQCが既に機能しており、P13後に開始するのは品質管理そのものではなく、製品全体に対する**検査強度と作用範囲を拡げる集中的なQC**である。

### 9.2 P13完了後の追加機能と品質管理の実行関係

1. **P13進行中**：現在の`PRODUCT_BUILD_MODE`とP13の有限受入を維持し、緩衝機能の施工は割り込ませない。この期間も既存開発はQC運用である。
2. **P13完了後**：ユーザーの明示施工指示により、D4Pocket全ボトルネックの全数観測、原因追跡、緩衝設計、実作用、修正・再試験を**集中的QCと一体で**進める。B0〜B6は「QC開始前の準備期間」ではなく、このQC循環を具体化する作業群である。
3. **統合候補凍結**：緩衝を含む機能境界と局所受入が成立した製品状態を、現行rev5の指定手順に従って新しいQ0候補へ結び付ける。過去の2026-10-07 Q0/Q1を新しい製品状態の合格証拠へ転用しない。
4. **最終統合QC**：Q1〜Q6で、緩衝の実効果と既存機能の品質を同時に検査する。不具合発見時には上流へ帰還し、設計/実装/介入を是正して再度候補を固定する。Q7の正式公開・署名などのOwner判断をCodexが代行しない。

**重要：**「B0〜B6が完了するまで品質管理を始められない」「Q0が始まって初めてQCに入る」とは解釈しない。一方、既存rev5のQ0〜Q7を勝手に開始・再定義することも禁止する。強化QCのうち既存の公式Q段階に属する作業は、現行modeと対象候補・Owner命令を満たしてから実施する。

### 9.3 既存Q0〜Q7への試験追加

| 既存工程ID（旧資料名を保持） | QCで確認する緩衝作用 | 固定して守る条件 |
|---|---|---|
| Q0 製品候補凍結 | P13後の緩衝を組み込んだ新しい対象commitと全ての関係成果物を固定 | 2026-10-07の旧凍結/Q1履歴を改変しない |
| Q1 横断 | Agent Task→Broker→調停→元Tool→結果・証拠の実接続と既存全機能 | 既存Task/Compare/Handoff/Workspace等の成立を省略しない |
| Q2 障害・復旧 | 既存`FQ-TEST-LOOPBACK`、TLS、crash、cancel、corrupt、replay、部分適用からの復元 | 根因不明・単独retry成功を修復成功にしない |
| Q3 安全・権限 | 調停の権限昇格・secret漏洩・Host越境・OS保護無効化・意味違反を拒否 | Authority/Permission/Approval/Audit/Recoveryは既存Ownerのみ |
| Q4 長時間・性能 | 8h/24hの実測反復、時間・資源・品質・緩衝規則の持続性 | 短時間成功やfixtureを長時間結果にしない |
| Q5 配置済み製品 | Windows clean install/別User/OneDrive/Update/Recoveryから緩衝の製品入口まで | 開発環境とinstalled製品証拠を分離 |
| Q6 正式証拠 | 同一候補のsource、変換規則・Toolchain・artifact hashと実QC結果を結ぶ | 旧候補のPASS/FAILを付替えない |
| Q7 Owner最終判断 | 製品状態を踏まえた正式公開・署名・不可逆判断 | Owner判断はCodexへ移譲しない |

### 9.4 QC不適合への帰還規則

不適合の発見時は、(a)観測環境と証拠、(b)元要求との不一致、(c)原因/仮説/未知、(d)変える必要がある条件、(e)局所是正、(f)再試験と他機能への波及、(g)同一候補への適用可否を明確にする。**重大な発見なら仕様・工程・検証器を含め上流まで戻る。** 発見時の証拠を旧候補へ残し、新しい候補に対する必要な統合検査を行う。これはQCの通常循環であって、『最後のQAで不良が見つかった』という例外扱いではない。

## 10. 非主張・未決定事項

- この設計はまだ動作する緩衝基盤の実証ではない。課題の全数監査も未了。QC思想を採用した事実だけで品質が成立したとは言わない。
- 実際の配置（Broker内/外）、Schema版、隔離方式、OS別導入、ABI変換可否、長時間負荷特性はB0/B1監査後に決める。
- P13のCLOSED条件、現行mode、release gate、`task_execution=unsupported`、`release_ready=false`をこの提案だけでは変更しない。
- 最終rev5原本3点の逐条照合と差分採否は未了。確認前に「rev5正本へ統合済み」と表現しない。QCという新たな上位方針を理由に既存の正式識別子を無断改名しない。
- 仕様の不足・矛盾が見つかったときは要求原文・目的まで戻して再評価する。理由なく対象や目的を削らない。
