# GUI Shell編集提案の意味正本

## 目的

`GUI Shell編集提案`は、Owner／Developerが明示開始した実装Agentの要求を、構成・UI・Contractの変更候補として審査待ちへ記録する開発経路である。製品Runtimeが自分自身を変更する機能ではない。

## Broker経路

Owner資格経路から編集指示、対象path、予定変更を認証済みRust Brokerへ渡す。Brokerは版、識別子、範囲、対象path、規約確認、自己承認禁止、`proposal_only`を再検証し、`INTERNAL_STATE`のAuditEvent付きReceiptを返す。指示本文はReceiptへ返さず、要求hashだけを結合する。

DesktopのSettingsからは、Windows起動器またはLinux／macOS用のネイティブ確認経路を通す。ネイティブ側で提案を検査し、提案ID、範囲、対象ファイル数、予定変更数と要求hashを表示する。確認した当該要求だけをBrokerの専用経路へ渡す。元の入力画面で指示と対象を確認できる。通常IPCおよび確認の拒否からは提案を受理せず、Brokerは確認済み要求の再送も拒否する。

## 適用範囲

対象pathは`apps/desktop_flutter`、`packages`、`specs`、`docs`、`tooling`、`native/rust_helper/src`、`規定`の境界内に限定する。`.git`、Manifest、release evidence、secret、credential、private、signingに関係するpathは拒否する。外部Agentのmetadataや履歴はAuthority、Permission、Approvalを生成しない。

## 自動適用禁止

現行単位の`execution_mode`は`proposal_only`、`review_required=true`、`apply_status=not_started`、`files_written=false`に固定する。編集Agentの提案をそのままapplyせず、Owner／Developerが差分、Contract、テスト、監査、権限境界を確認してから、別の明示的な開発作業として実装する。自己承認、Permission生成、Approval迂回、秘密値取得は行わない。

## Agent Centerへの別Task受け渡し

Settingsの編集提案画面は受理Receipt後、指示本文、対象path、予定変更、指示hash、Audit IDをOwner／Developerが確認できる。明示的な確認後、本文とReceipt参照を未信頼contextとしてAgent Centerへ渡し、登録済みSessionの選択後に既存Agent作業要求検査だけを行う。Agent Centerの事前検査Dialogでは内容を固定表示し、MCP能力追加を要求しない。

この受け渡しはproposalの自動applyではなく、独立した通常Broker Task要求の準備である。受け渡し自体はPermission、Approval、Credential、Agent trust、Task実行を生成・継承しない。target_pathsはTaskの希望範囲であり、OSまたはBrokerのアクセス境界ではない。実際のアクセス範囲はBroker Workspace Permissionが決める。Task指示は対象path内に限定し、必要範囲が合わない場合は書込み前に停止してOwner／Developerへ報告する。通常Broker経路で現在のWorkspace PermissionとTaskごとの一回Owner Approvalを別々に取得する。Task事前検査が成功するまで下書きを保持し、取消・Broker拒否時は下書きを消費しない。受理後もファイル変更や実行完了と誤表示しない。

## 完了結果からの制御適用Task準備

完了したAI Edit Taskの結果を別Workspaceへ引き継ぐ場合、Agent Centerは、元proposalのedit ID／要求payload hash／Audit ID、元Task ID／指示hash、Brokerが返した完了状態とresult hash、現在のContent Exposure許可がすべて一致したときだけ結果を表示対象にする。Owner／Developerがfull Content Exposureを別途許可した場合は、boundedな結果本文に加えてsummary・changed files・diff・test結果を表示できる。これらAgent申告は未検証として表示し、検証済み事実または実ファイル差分として扱わない。

結果を実装Agentへ渡す操作は、元Sessionとは異なるSessionかつ異なるWorkspaceで、Broker登録状態が利用中であり、Task要求／Task記録がまだない場合に限る。Owner／Developerが適用範囲を明示入力した後、D4 Pocketは提案・結果・出所ID/hash・入力範囲を未信頼contextとして通常のBroker Task要求へ束縛し、事前検査だけを行う。適用先要求は`require_unused_task_session=true`を要求し、Brokerは耐久Audit上のTask開始履歴を事前検査・Owner Approval発行・Task開始の各時点で照合する。履歴の本文や一覧はこの照合から表示せず、履歴の破損・読取失敗はfail-closedとする。この条件はPermissionやApprovalを生成しない。元Task・結果projection・proposal provenance・対象Sessionの識別、Workspace、Audit結合、完了状態、結果本文を操作前、入力待機後、Broker応答後に再照合する。不一致や途中変更があればTask準備を停止する。

この機能は結果の直接適用ではない。事前検査からWorkspaceへの書込み、Task開始、Permission／Approval発行を行わない。準備された適用Taskは通常のAgent Task経路へ戻し、対象WorkspaceのPermissionとTaskごとの一回Owner Approvalを別々に新規取得する。提案・結果からPermission、Approval、Credential、Trust、Authorityを継承しない。Flutterはfilesystemやprocessを直接操作しない。結果本文とAgentの変更・test申告は未信頼データのまま保持する。

適用Taskは別Session／別Workspaceの実装作業として、提案元Agentのsummary・changed files・diff・test申告を証拠とせず、変更前の適用先Workspaceを確認し、Owner／Developerの指示と現在のWorkspace Permissionの範囲内で作業する。適用先で関連test／検査を新たに実行し、正確なcommand・exit status、実際に観測した変更file／diff、Recovery状態を報告する。実行不能は`NOT_RUN`、失敗は`FAIL`として残し、Broker Workspace Inspectorで照合するまではAgent申告と明示する。この指示やその実行結果は検証・Approval・Authorityを生成せず、適用元Workspaceへの直接書込みも許可しない。

## 実際の差分の審査

Settingsの受理済み提案から「実差分を審査」を開く。Workspace Inspectorで候補の登録を選び、変更前に保存した全体基準点と、現在のfull読取承認を使って「提案範囲と実差分を照合」を実行する。

Brokerの `GUI Shell編集提案審査` は、現在のHost表示世代における永続監査の受付事象を元の提案と照合する。登録hash・全体基準点hash・読取承認の一致を確認し、登録rootの既存取得器で現在の版を取得する。除外された秘密パスを表示せず、許可対象外の変更を発見した場合は差分の返却を拒否する。受理時は、変更ファイルの前後の版、差分hash、受付参照と審査の監査IDを結ぶ。表示は取得時点の内容であり、適用や復旧には現在の条件に結ばれた独立の権限が必要になる。

審査後は「適用先を照合」から、別のfull読取承認を得た登録済みWorkspaceを選択できる。Brokerの `GUI Shell編集適用先照合` は、変更対象の相対pathと前後の版hashを審査の永続監査に照合する。審査元と適用先の登録rootが同一または包含関係にある場合は拒否する。既存の取得器で、審査元の現在版が審査時の変更後版、適用先の現在版が審査時の変更前版と一致することを確認する。承認失効、版の変化、取得拒否があれば照合結果を返さない。

適用先照合が返すのは、対象path、版hash、審査と照合の監査参照である。照合時点の情報を利用者に表示し、権限やファイルの状態は変更しない。制御適用では、別のOwner確認に加え、書込み時点の版の再照合と復旧が必要になる。

## 制御適用と復旧で使うファイル移動

編集前の版を退避し、復旧で戻すときは、同一volume上の登録済みdirectory handleを使う。既存のパスと秘密の検査を通し、移動前のファイル識別子と内容hashを照合する。OSの置換禁止付き移動で、別プロセスが宛先を確保していた場合は両方の版を保持する。Windowsでは共有を許可せず開いた同期I/Oのファイルhandleを、`NtSetInformationFile` と宛先directory handleで移動する。 [Microsoft FILE_RENAME_INFORMATION](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information)

移動後は元の名前の不在と、宛先のファイル識別子・内容hashを確認する。移動前の拒否と、移動後に競合を観測した状態は区別する。後者では宛先を保持し、復旧記録から副作用を確認する。ファイル移動を呼び出すBroker操作は、実行前に現在のOwner認可と復旧記録を確定する必要がある。

複数ファイルの適用では、審査済みの変更後版を、呼出し元が隔離した同一volumeの退避先へ準備する。適用前に、審査結合のhash、適用先と退避先の実体ID、対象パスと変更前後の版を既存のBroker保管鍵で認証して保存する。適用時は各移動の直前に有効期限とファイルの版を確認し、完了時は適用結果と退避版を突き合わせる。

適用中断または独立承認後のロールバック中断は、耐久記録とファイルの現状態を照合して復元する。照合できた対象だけを戻し、別の版が作られた場合はその版と退避済みの版を保持する。適用が確定した記録では、明示されたロールバック承認を待つ。

同じ審査と物理Workspaceに結び付く既存Journalを検出した場合、再発行された適用要求hashを旧Journalへ流用しない。Broker保護鍵でJournalを検証し、記録済みの元hash・Workspace実体IDに束縛して未完了の補償回復だけを行い、新しい適用は拒否する。改ざん・別Workspace・外部版競合はfail-closedとし、回復状態をAuditへ記録する。

## Owner確認後の適用

Workspace Inspectorの適用先照合が完了したら、「Owner確認して適用」で、対象パスと追加・置換・削除の内訳、審査差分のhashをネイティブ確認に表示する。Brokerは審査と適用先照合の耐久監査、現在の読取承認、ファイル版を照合する。対応する作業領域に実行中のAgent Taskがあれば適用を拒否する。同じ審査を同じ物理作業領域に適用できるのは一回である。

適用には、作業領域と同じvolumeにあるBrokerの保護保管先を使用する。確認の消費を監査へ記録してから書き込む。適用後の版と復旧記録を確認し、完了監査を保存してから、画面に適用件数と復旧記録IDを表示する。完了監査の保存に失敗した場合は照合できる版を元へ戻し、監査エラーを返す。

## 独立した明示Rollback

適用成功結果には、Rollback要求を組み立てるための元適用要求・要求hash・Apply Audit IDを結果画面の一時状態として保持する。これらは対象とAuditの照合材料であり、旧Owner確認やApprovalとして再利用しない。Workspace Inspectorの「別のOwner確認でRollback」は専用の`GUI Shell編集Rollback` Broker操作を呼び出し、現在のHostに存在する成功Apply Audit、同じWorkspace登録、現在のfull Workspace Permission、適用中Agent Taskの不在を再確認する。

Rust Desktop Nativeは元適用とは別のRollback要求hashに束縛した確認内容を表示する。確認後、Brokerは同一volumeの保護退避先とHMAC Journal、適用時の実体ID、各対象の現在hashを再照合する。追加fileは適用版だけを除去し、置換・削除fileは変更前版だけを復元する。別プロセスが作った版、root変更、登録・Permission失効、Audit不一致を検出した対象は上書きせず、差分とJournalを残して拒否する。

Rollback開始意図を耐久Auditへ先に記録し、各移動の直前にも現在Permission期限を確認する。成功時は`rolled_back`、対象件数、Transaction IDと完了Auditだけを返す。中断したRollbackはJournalの`Reverting`／`RecoveryRequired`状態から、改めて現在Permissionと新しいNative確認を得た後に再開できる。再開時も既に復元済みの変更前版を再適用せず、各fileの現版と退避版を照合する。本文やCredentialは応答・Auditへ含めない。

Rollback操作は現在、成功直後の結果画面から起動する。画面を閉じた後やアプリ再起動後に、過去の適用一覧からRollback対象を再発見するConsumerは未接続である。適用途中の自動補償Recoveryとは別の制約として保持する。
