# GUI-Shell 日本語基底規定

> 状態: 現行局所正本
> 版: `2026-09-02-日本語基底-1`
> 規定言語・基底言語: 日本語
> 適用範囲: GUI-Shell が所有する文書、意味、設計、契約説明、実装上の独自概念、監査、検証、運用報告

## 0. 位置づけ

本規定は、GUI-Shell における日本語基底の局所正本である。

GUI-Shell では、対象、差異、関係、状態、作用、境界、権限、採否、失敗、復旧、検証結果を、最初に日本語で成立させる。

```text
日本語で対象化・差異化・関係化
→ 日本語で定義・設計・構造化
→ 日本語で実装意味・監査・検証を記述
→ 日本語正本成立
→ 実務上やむを得ない外部接続だけ他言語へ局所射影
```

外国語を第二基底、並列正本、内部意味の主語として扱わない。

本規定は次と責任を分ける。

- `AGENTS.md`: 作業規律、優先順位、安全・権限・Git・検証・完了報告の正本
- `規定/正本索引.json`: 現行正本、責任地図、外部参照固定点の機械可読索引
- `docs/LANGUAGE_POLICY.md`: Flutter / Dart、Rust、TypeScript / Node、Python 等の実装言語・実行責任の分担方針

自然言語の日本語基底と、プログラミング言語の採用方針を混同しない。

## 2. 日本語を正本とする対象

GUI-Shell が独自に所有し、外部契約に表記を拘束されない次の対象は、原則として日本語で保持する。

- 規定、仕様、設計、責任、境界、前提、成功条件、失敗条件
- 操作者向け文書、導入文書、運用文書、復旧文書、監査報告
- 独自の対象名、状態名、作用名、関係名、権限名、採否名、失敗分類
- 契約の意味説明、Schemaの責任説明、ProtocolのGUI-Shell側意味
- 監査語彙、検証項目、試験名、fixtureの意図、失敗理由
- ログの意味区分、診断説明、利用者へ表示するメッセージ
- 実装上の独自コメント、docstring、内部概念名
- GUI-Shell が新設する独自の構造化データ鍵・区分値・識別子
- 変更理由、証拠範囲、未検証範囲、残存リスク、再開放条件

既存の公開契約、互換識別子、保存形式を日本語化する場合は、表記変更自体を目的にせず、互換性、移行、復旧、監査、利用者影響を先に閉じる。安全な移行契約なしに既存識別子を一括改名しない。

## 3. 他言語を認める局所例外

次は、正確性、相互運用性、実行可能性、検索再現性、既存互換性のため必要な範囲に限り、原形を保持できる。

1. プログラミング言語の予約語、標準構文、演算子、型構文
2. 外部API、外部Schema、通信規約、Protocolが要求する固定フィールド・固定値
3. 既存ライブラリ、framework、package、crate、module、class、function、typeの正式識別子
4. CLI の command、option、environment variable、filesystem path、branch、tag、ref
5. URL、commit hash、署名、digest、版識別子、言語コード
6. JSON Schema、IPC、HTTP、Git、SHA-256等の規格・形式・Protocol名
7. GUI Shell、Runtime Operation Shell、Shell Core、BLUE-TANUKI、Flutter、Dart、Rust等の固有名・確立用語
8. Capability、Permission、Approval、AuditEvent、RecoveryAction等の既存公開契約識別子
9. `release_blocker`、`post_v1_scope`、`known_limitation`等の機械判定値
10. 外部模型、製品、組織、論文、方式、規格の固有名
11. 原文引用、由来保存、検索、国際公開、外部連携に必要な外国語表層
12. 自動生成物、vendor由来物、lockfile、binary等、GUI-Shellが本文言語を所有しない対象

例外は、必要な接続面とその近傍だけに閉じる。英語で書きやすい、業界で一般的、既存文書が英語という理由だけで、GUI-Shell独自の意味正本を英語にしない。

例外表記が必要でも、その役割、境界、採否、失敗時挙動、監査結果は日本語で説明する。

## 4. 外部原語と確立用語の扱い

外部原語を観測した場合、原語の一般語義からGUI-Shellの内部意味を逆定義しない。

```text
外部原語・確立用語
→ 対象・作用・関係・状態・境界へ分別
→ GUI-Shellで必要な日本語意味を定義
→ 原語は外部対照名または機械識別子として保持
```

例:

```text
runtime
→ 実行対象 / 実行系 / 実行中状態 / 製品実行経路を文脈ごとに分別

state
→ 模型状態 / 作業状態 / UI局所状態 / 外部再入力状態 / 永続状態を分別

approval
→ 承認要求 / 承認資格 / 承認状態 / 承認証跡を分別
```

日本語でどの対象・差異・関係を指すか確定できない場合は、都合よく補完せず、未確定としてSUSPENDまたは調査対象にする。

## 5. コード・Schema・Protocol

コードも日本語基底の適用外ではない。ただし、実行可能性と既存契約を壊してはならない。

- GUI-Shell独自の新規概念は、実装環境が安全に許す場合、日本語識別子を優先する。
- 外部API、言語慣行、framework契約、公開Schemaとの接続識別子は原形を保持する。
- 既存の英語識別子を維持する場合、日本語の責任説明から参照できる状態を保つ。
- comment、docstring、試験意図、失敗説明、運用ログは、外部制約がない限り日本語を正本とする。
- Schemaの英語field名は、その一般語義だけで権限・信頼・承認意味を決めず、日本語仕様へ接続する参照札として扱う。
- 機械値の改名は、互換移行、旧版読取、rollback、negative test、監査証跡を伴う契約変更として扱う。

## 6. 既存英語資産の移行

本規定の成立だけで、既存リポジトリ全体の日本語基底移行が完了したとは扱わない。

既存英語資産は、次の順に境界を固定して移行する。

1. 正本、現行仕様、運用指示、利用者向け文書、履歴、生成物、外部由来物を区分する。
2. 表記ではなく、対象・責任・差異・関係・禁止・失敗条件を読み取る。
3. 日本語で意味正本を成立させる。
4. 外部識別子と日本語意味の対応を保持する。
5. 既存契約・link・test・tooling・runtimeへの影響を検証する。
6. 旧版・旧表現を無言削除せず、必要な履歴と移行根拠を残す。

機械翻訳、一括置換、file名だけの改名、英単語削減率を移行完了の証拠にしない。

## 7. 意味監査

日本語基底監査は、単なる日本語文字率を評価しない。少なくとも次を確認する。

- GUI-Shell独自概念の主語が日本語で成立しているか。
- 対象、状態、作用、関係、権限、境界、採否、失敗が日本語で区別されているか。
- 外部原語の一般語義が内部分類を支配していないか。
- 日本語で保持できる差を外来語一語へ圧縮していないか。
- 多言語例外に実務上の必要性があり、局所境界に閉じているか。
- 外部識別子を削除しても、日本語説明だけで責任と安全境界を再構成できるか。
- 日本語正本と外部表層が衝突したとき、日本語正本へ戻って再監査できるか。
- `規定/正本索引.json` の責任地図、参照commit、現行正本が実ファイルと整合するか。
- language migrationが権限、Approval、AuditEvent、RecoveryAction、Content Exposure Boundaryを弱めていないか。
- 文書の日本語化をruntime、contract、releaseの完成証拠へ読み替えていないか。

翻訳または外部接続で未定義、意味衝突、関係欠落が見つかった場合、外国語側で補完せず、日本語正本を先に再監査する。

## 8. 禁止事項

- 英語名を先に作り、日本語訳を後から正本と称する。
- 日本語と英語を独立した並列正本にする。
- 外部APIやframeworkの語彙粒度をGUI-Shellの内部概念へそのまま写す。
- 外部方式名・製品名を構成要件へ無言昇格する。
- 翻訳しやすさのために日本語で保持できる差異・関係・未確定性を削る。
- 日本語化を理由に、Schema、Protocol、保存形式、公開API、CLI互換性を無計画に破壊する。
- 上位理論、LLM成立規定、MINIDORAの本文や局所実装をGUI-Shellの正本として丸写しする。
- LLM、外部metadata、memory、cache、GUI state、translation resultから権限を生成する。
- HDSの非公開内部を記述、類推、転記、再構成する。
- MINIDORAのv8参照とLLM成立規定のv9を同一版として黙って統合する。
- 外部参照のmain更新をGUI-Shellへ自動適用する。
- 日本語文書の存在や監査scriptのPASSだけで製品完成・release readinessを主張する。

## 9. 版更新と再開放

本規定の意味、対象、例外、監査条件を変える場合は版を更新し、少なくとも次を記録する。

- 何が変わったか。
- なぜ変わったか。
- どの既存文書・実装・契約・試験へ影響するか。
- 何を維持するか。
- 何を再開放したか。
- rollback可能な旧版はどれか。

外部参照commitを更新するときは、旧版との差、GUI-Shellへの適用射程、採用事項、不採用事項を監査する。最新版であることだけを採用理由にしない。

本規定自身も監査対象である。日本語基底がGUI-Shellの意味構造保持、安全性、操作明瞭性、相互運用性を損なう具体的観測が得られた場合は、言語だけでなく、対象、目的、損失、評価方法、例外境界まで再開放する。
